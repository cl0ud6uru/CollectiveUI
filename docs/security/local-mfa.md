# Local passkeys and TOTP

Implemented on a draft branch, verified 2026-10-03. Base: `659eb856c21acff3a7ef9be34e7d8e25ffd26fe4`.

## Coverage and assurance

Local accounts only. Entra continues to delegate authentication/MFA to its IdP; this change does not assert or enforce an Entra assurance level. LDAP keeps its current password bind behavior, including the existing hybrid directory identity shared with Entra. Local identities remain separate even when email or UPN matches. No automatic linking, forced enrollment, or new administrator policy.

A passkey is passwordless authentication with required user verification (device PIN/biometric), not a claim that a credential is hardware bound. Discoverable credentials support synced passkeys, mobile hybrid authentication and security keys. TOTP is a second factor after a password. Once either factor is enrolled, password-only local authentication is refused at the provider boundary, including direct Auth.js callbacks. A password plus a single-use recovery code is the lost-device path.

## State and trust boundaries

Use maintained SimpleWebAuthn for WebAuthn and otplib for RFC 6238. Do not implement signature/CBOR/TOTP primitives. Reuse Node crypto and the application's AES-256-GCM keyring for encrypted TOTP storage with account-bound AAD; require an explicitly configured key even in development. No secret retrieval in admin APIs.

Use `@collective/webauthn-server` and `@collective/webauthn-browser` npm aliases for SimpleWebAuthn 14.0.3 / 14.0.0, avoiding Auth.js’s older optional WebAuthn peer dependencies; Auth.js’s experimental WebAuthn provider is not used. otplib is pinned to 13.5.0.

Store one-shot, random 256-bit proofs as hashes in PostgreSQL with purpose, expiry, browser/session binding and account session version. Password checks create a scoped preauthentication proof, never an application session when factors exist. Completed authentication creates a short-lived ticket consumed by the local Auth.js provider; the provider rechecks current account state. Auth.js retains its CSRF and session-cookie handling. A fresh HttpOnly, SameSite=Strict, host-only browser binding protects preauthentication and ticket exchange; HTTPS uses a __Host- cookie. All ceremony and management POSTs require exact configured Origin and JSON; no Host-derived RP configuration.

Recent reauthentication is single-use and bound to the current signed-in session, account version and intended operation. It requires a verified passkey or password plus the existing TOTP/recovery factor; an unprotected account uses its current password. Enrollment is unavailable with temporary passwords. Each ceremony expires, is consumed before verification (including failed attempts), and rechecks disabled/version/provider state under the same transaction lock used by account reset/revocation. TOTP pending secrets activate only after proof; acceptance uses a narrow clock window and stores the last accepted time step. Recovery codes each contain 160 random bits, are stored only as account-bound hashes, consumed atomically and replaced on regeneration. Spending the final recovery code automatically creates a new set, revokes sessions and returns the codes once, avoiding a lost-device user being stranded with no code left for enrollment reauthentication. Login pauses for a save acknowledgement before exchanging its new-version ticket. During management the requested change is deferred: save the new codes, sign in again, then retry. An expired login ticket keeps the new codes visible so the user can restart with a saved code.

Passkey credential IDs have global uniqueness; opaque per-account user handles carry no email/UPN. Assertions must match both credential ownership and userHandle, challenge, exact origin, RP ID and UV. Cross-origin clientData and any topOrigin are rejected explicitly, including the library’s permissive Safari compatibility case. Anonymous discovery cannot identify an account at challenge creation, so every revocation/password/access change stamps `users.auth_changed_at` using the database clock. Passkey completion rejects challenges created at or before that timestamp under the account lock. Counter updates serialize; the maintained verifier rejects nonzero counter regression and permits zero-only synced authenticators. Backup state is recorded without promising clone detection for synced credentials.

Every factor activation/removal, recovery-code regeneration and protection disable revokes all sessions and stale proofs through sessionVersion. Removing any passkey or disabling protection requires password-based full-factor reauthentication, proving the password fallback is usable; a passwordless user who forgot their password must change it first using a passkey. Removing the final factor is refused; returning to password-only requires an explicit disable operation after strong reauthentication. Sensitive events audit action/actor/target only. No raw library errors, assertion payloads, TOTP secrets, tokens or recovery codes in logs.

## Recovery and operation

Save recovery codes offline and enroll a second passkey. If a password is lost, existing authorized password reset issues a temporary password and revokes sessions but preserves all factors. Both ordinary admin and operator `recover-admin` preserve MFA; neither provides a secret read or MFA bypass. If all factors and recovery codes are lost, access remains blocked. Any exceptional offline reset requires a separate operational identity-verification/dual-control procedure and explicit authorization; there is no web or CLI factor-reset shortcut in this increment. No email recovery or delivery is added. Sessions predating this feature remain valid at their original version/expiry; the Security page asks those users to sign out/in to obtain a distinct per-session binding before management.

Deploy behind HTTPS with a stable `AUTH_URL`; `http://localhost:<port>` is supported for development only. RP ID is the configured origin's hostname, not browser input, and must stay stable. Changing host requires planned re-enrollment while old methods still work. Configure encryption keys before TOTP enrollment, preserve old key IDs during rotation, restrict database/keyring access and exclude sensitive request bodies from proxy/APM logging. Database backups containing encrypted secrets must be protected alongside keys.

- Existing `tests/integration/local-auth.test.ts`: eleven lifecycle/provider-isolation/reset/revocation tests passed on the disposable migrated database.
- `LOCAL_MFA_BROWSER=1` and a migrated `DATABASE_URL` ending in `/collective_local_mfa_browser_test`, `playwright test --config playwright.local-mfa.config.ts`: two browser scenarios cover UI enrollment, recovery, final-code recovery followed by regeneration, temporary-password change, mobile layout, no preauth session, valid-CSRF direct-password callback denial, actual virtual-authenticator registration/passwordless login, UV, ownership/userHandle, exact origin/RP/challenge/cross-origin checks, session revocation, and concurrent assertion/ticket replay. Adversarial payloads are re-signed with the disposable virtual authenticator’s key so invalid signatures do not mask missing validation. Synced credentials reporting repeated zero counters are accepted with fresh challenges; nonzero regression is rejected.

Browser fixture server: local-only Next development server on `http://localhost:3100`, disposable DB, synthetic `AUTH_SECRET` and a synthetic 32-byte base64 `ENCRYPTION_KEY`. The test config uses `/usr/bin/chromium` by default or `PLAYWRIGHT_CHROMIUM_PATH`. No actual keys or provider credentials are used. Test files enforce their disposable database names before mutation. Do not point these tests at an installation database. The migration test owns and rebuilds its named disposable schema.

Apply final migration `0021_local_factors` before running this application version. No UI admin policy forces enrollment. The operator must configure the stable HTTPS origin, encryption keyring, trusted-proxy policy and synchronized server clocks before voluntary enrollment. Account/source budgets are persistent: password limits remain 10 per account and 30 per source per 15 minutes; factor attempts are 5 per account per 5 minutes, security requests (including Auth.js ticket exchanges) 60 per source per 5 minutes and 120 globally per minute. Expired state and throttle rows are pruned during these requests. The existing shared local-account transaction lock serializes lifecycle changes and factor verification; this is intentionally conservative and should be measured before high-volume use.

Lost-all-factor recovery remains a separate operator procedure requiring authorization and strong identity verification. There is deliberately no web/CLI MFA-reset escape hatch. An already authorized in-flight response cannot be recalled. Physical Android/iOS/security-key compatibility and a real Entra/LDAP deployment round trip were not exercised; Chromium virtual authenticators verify standards-based support, not a physical-device compatibility matrix. FIDO conformance of the library is not certification of this application.

An independent agent reviewed the architecture and implementation. Initial medium findings (mixed legacy encryption-key validation, explicit WebAuthn cross-origin checks, password fallback lockout, final-recovery-code exhaustion) were fixed and covered by regressions. The reviewer inspected code/test evidence; it did not independently run the fixture suites. Final review found no remaining critical, high or medium blocker. Its last low-priority issue (honoring a recovery flag without an actually verified recovery factor on password-only accounts) was also fixed and covered by a database regression. The latest browser and database runs passed after that fix.
