# Routine admission limits (#320)

Five-field cron schedules must leave at least five minutes between selected hour/minute slots, including the midnight boundary. Validation checks the entire daily cycle, independent of the time a schedule is saved. This deliberately also rejects adjacent midnight slots on sparse calendar schedules. Five-minute, hourly, daily, weekday and monthly presets keep their timezone interpretation. Seconds fields and aliases are refused.

Manual, webhook and cron admission share a per-owner PostgreSQL transaction advisory lock. Counting queued/running rows and recording a new run use that same transaction and connection. Each owner can have at most three queued or running routine runs across their bots and trigger types. Manual and webhook attempts return 429 at the cap; the latter rechecks its enabled state, trigger and stored secret after obtaining the lock. Existing accepted rows remain durable when the queue is unavailable and the sweeper retries their original IDs. Completed/failed runs release capacity. Approval pauses retain their existing behavior and do not consume a background worker slot.

Scheduled ticks advance the calendar without adding work while the same routine is already queued/running or the owner is at capacity. Missed occurrences are coalesced, rather than accumulated for later replay. Existing invalid/frequent schedules receive no new run and their `nextRunAt` becomes null until the owner edits them. Existing queued work is retained. There is no schema change and no reduction of the shared worker's configured concurrency.

The opt-in integration suite requires an exclusive disposable database named `collective_review_routine_admission_test`; it runs no workers or model turns. Real PostgreSQL and pg-boss prove concurrent manual server actions, mixed-trigger contention, queued/running caps, admission by another owner despite a flood, advisory lock blocking/release, scheduler coalescing, validation through the save action, pause races, ownership checks, durable queue failure and capacity release. The queue recovery regression separately starts a synthetic routine exactly once without executing its agent/model turn. CI requires both pool=1 and pool=4 admission proofs, plus the recovery regression.

Parity: the web editor's interval presets already start at five minutes. iOS and macOS expose routine results in Inbox/conversations and have no routine editor or manual-run surface. Shared server policy applies to all callers; no client UI or contract changes are needed. Native runtime behavior is not exercised by these server-only checks.
