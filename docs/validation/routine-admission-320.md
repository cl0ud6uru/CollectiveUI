# Routine admission limits (#320)

Five-field cron schedules must leave at least five minutes between selected hour/minute slots, including the midnight boundary. Validation checks the entire daily cycle, independent of the time a schedule is saved. This deliberately also rejects adjacent midnight slots on sparse calendar schedules. Five-minute, hourly, daily, weekday and monthly presets keep their timezone interpretation. Seconds fields and aliases are refused. In addition to the complete daily slot check, actual elapsed gaps to the previous and following occurrence are checked around the candidate using separate cron-parser iterators. A daylight-saving jump may make a schedule invalid when that boundary approaches; validation is repeated at scheduler ticks. The due occurrence is also checked, including an exact/late tick after the short gap. Invalid legacy schedules receive no run and pause (`nextRunAt=null`) until edited. This does not reject a valid five-minute schedule merely because its next occurrence is seconds away.

Manual, webhook and cron admission share a per-owner PostgreSQL transaction advisory lock. Counting queued/running work and recording a new run use that same transaction and connection. Each owner can have at most three queued or running routine runs across their bots and trigger types, including background agent work retained after its routine is deleted. Manual and webhook attempts return 429 at the cap; the latter rechecks its enabled state, trigger and stored secret after obtaining the lock. Existing accepted rows remain durable when the queue is unavailable and the sweeper retries their original IDs. Completed/failed runs release capacity. Approval pauses retain their existing behavior and do not consume a background worker slot.

Scheduled ticks advance the calendar without adding work while the same routine is already queued/running or the owner is at capacity. Missed occurrences are coalesced, rather than accumulated for later replay. Existing invalid/frequent schedules receive no new run and their `nextRunAt` becomes null until the owner edits them. Existing queued work is retained. There is no schema change and no reduction of the shared worker's configured concurrency.

The opt-in integration suite requires an exclusive disposable database named `collective_review_routine_admission_test`; it runs no workers or model turns. Real PostgreSQL and pg-boss prove concurrent manual server actions, mixed-trigger contention, queued/running caps, admission by another owner despite a flood, advisory lock blocking/release, scheduler coalescing, validation through the save action, pause races, ownership checks, durable queue failure and capacity release. The queue recovery regression separately starts a synthetic routine exactly once without executing its agent/model turn. CI requires both pool=1 and pool=4 admission proofs, plus the recovery regression.

Parity: the web editor's interval presets already start at five minutes. iOS and macOS expose routine results in Inbox/conversations and have no routine editor or manual-run surface. Shared server policy applies to all callers; no client UI or contract changes are needed. Native runtime behavior is not exercised by these server-only checks.

Independent review reproduced the spring-DST defect before repair: `0,59 1,3 * * *` in America/New_York allowed 01:59 EST followed by 03:00 EDT (one elapsed minute). Three unit regressions failed, and the actual PostgreSQL scheduler admitted the 03:00 occurrence when its later neighbor was safe. These pass with the correction. Dedicated fixture guards now require explicit opt-in, exact named database and known synthetic credentials, loopback IP with explicit port, no query/fragment and no PG connection overrides; both admission and destructive outbox proofs are guarded.

Correction verification: 53/53 unit cases (schedule neighbors and pure target guards), 11/11 actual PostgreSQL admission cases at pool=1 and again 11/11 at pool=4, four selected scheduler/outbox rollback regressions, and one pg-boss recovery/exactly-once-startup case. Typecheck, changed-file ESLint and diff checks pass. Local PostgreSQL is portable 16.14 with vector 0.8.1; hosted CI remains required at the published head. No worker agent/model turn ran.

Retained-work correction: deleting a routine cascades its `routine_runs` rows and sets each retained agent's `routineRunId` to null. The original cap only joined the deleted routine/run rows. Real PostgreSQL reproduced the bypass through the actual save, manual admission, routine runner and delete actions: after deleting three source routines, three queued or claimed-running background agents remained, but a fourth run was accepted. Both deletion regressions failed before this correction while the original 11 cases passed.

Admission now selects ordinary active routine runs and orphaned active background agents in one `UNION ALL` statement under the existing owner lock. The orphan branch requires the same agent/conversation owner, a routine-source conversation, `background=true`, no linked routine run and queued/running status. Linked work is counted only by the ordinary branch. One statement gives both branches the same PostgreSQL snapshot, so a concurrent delete cannot fall between separate counts. Foreground chat, unrelated background work, approval pauses and terminal agents retain their existing admission behavior. Deletion still retains agent work; no queue, cancellation, schema or worker-concurrency policy changes.

Retained-work verification: 15/15 actual PostgreSQL admission cases at pool=1 and 15/15 at pool=4, including queued/running deletion loops, other-owner admission, exactly one slot released by completion, no double-count of still-linked agents and exclusion of ordinary-chat/foreground/paused/finished agents. Four scheduler/outbox regressions, the pg-boss recovery case and 53 unit cases also pass. Typecheck and changed-file ESLint pass. The new deletion proof blocks HTTP fetches, creates durable agent rows/jobs without launching an agent worker or model turn, and uses the guarded disposable loopback fixture. Hosted CI remains required at the final published head.
