# Browser device login for a private stock Codex runtime

This change makes the website’s stock Codex connection usable without the SIWC Mac companion, token import, a local email binding, or a rewrite of either harness. It does not deploy or activate an installation. The parent task coordinates merge, image publication, VM changes and owner approval.

## Scope and compatibility

The supported implementation is the Docker owner-isolated stock app-server at **0.163.0-alpha.2**, source **a6274249d5877030676db098914db686bab7c921**. Direct text turns, native command/file results, retained threads, Stop, and decline-only approval controls remain the existing harness. Attachments, groups, routines, delegation, and device login in the SBX backend are outside this delivery.

The installed desktop app CLI was 0.131.0-alpha.9 and was not used as evidence for the pin. A separate exact npm `0.163.0-alpha.2-darwin-arm64` artifact was downloaded to scratch, checked against registry SHA-512/SHA-1, and run with empty scratch HOME/CODEX_HOME. Its `--version` and stable/experimental generated app-server schemas confirmed:

- `account/login/start {type:"chatgptDeviceCode"}` returns loginId, verificationUrl and userCode, not tokens.
- `account/login/cancel {loginId}` returns `canceled` or `notFound`; completion reports success with optional loginId/error.
- Experimental `account/read.workspaceRouting` provides the account/workspace ID. The client already opts into experimental API. Missing routing fails confirmation closed.
- `chatgptAuthTokens` is marked internal-only in this pin. No use of this mode or token export was added.

The validated Darwin tarball SHA-256 was `f43299734a9bee851b1ad8dd4a61c07ca8ece3150e3336bbf75e5c1216b68b7e`. Decoded npm provenance matched the pinned release tag and source commit; its signature was not independently verified. This is binary/schema validation, not a Linux sandbox test. The Linux image still verifies the existing archive and binary checksums in `docker/personal-codex/stock-inputs.lock.json`.

The same empty-home binary completed `initialize`, `config/read` and signed-out `account/read`, confirming native `model_provider=openai`, `forced_login_method=chatgpt`, file credential store, and empty shell inheritance. Pinned `account_processor.rs` also confirms logout cancels `ActiveLogin` before revoking stored auth, so broker restart cleanup does not need a lost loginId. This was checked in source without initiating a live device grant.

Codex is Apache-2.0 and OpenClaw’s inspected pinned provider/reference package is MIT. No OpenClaw source was copied. OpenClaw’s host-owned profile/token-refresh design differs from the Codex-owned credential lifecycle used here. Independent native-provider reuse was investigated but not implemented: no Codex grant is sent to the public SIWC Responses endpoint. The native harness and its SIWC connection remain independent.

Sources: [pinned account protocol](https://github.com/openai/codex/blob/a6274249d5877030676db098914db686bab7c921/codex-rs/app-server-protocol/src/protocol/v2/account.rs), [pinned device implementation](https://github.com/openai/codex/blob/a6274249d5877030676db098914db686bab7c921/codex-rs/login/src/device_code_auth.rs), [Codex license](https://github.com/openai/codex/blob/a6274249d5877030676db098914db686bab7c921/LICENSE), [OpenClaw reference](https://github.com/openclaw/openclaw/blob/e106d1fa54ec11e55cbd23d17334a99e7492c2b7/docs/plugins/codex-harness-reference/auth.md), [OpenClaw license](https://github.com/openclaw/openclaw/blob/e106d1fa54ec11e55cbd23d17334a99e7492c2b7/LICENSE).

The official [app-server auth guidance](https://learn.chatgpt.com/docs/app-server#auth-endpoints) restricts commercial/hosted service usage and directs those integrations to SIWC. This implementation and validation target the requested private owner-paid runtime; they make no claim of approval for a public commercial hosted service.

## Exact deployment requirements

1. Build and distribute **web, worker and host broker from this same reviewed commit**. The reported app image `2508f659` alone predates these changes. The broker runs `node --import tsx src/personal-codex/main.ts`; replacing only web/worker will not add the new lifecycle or auth-mode behavior. No new database migration is added; the existing journal through `0057_chatgpt_companion` must already be applied.
2. Build a **new stock wrapper image** on Linux amd64 using `PERSONAL_CODEX_DOCKER_EXECUTABLE=/usr/bin/docker bash scripts/build-personal-codex-stock.sh`. This keeps the official prebuilt binary pin and does not compile Rust. Publish/pull through the owner’s approved image workflow, record the immutable digest and local complete image ID, and use that exact ID in broker config. Do not reuse the old wrapper image just because its binary has the same version.
3. Keep the existing reviewed AppArmor/seccomp profile and narrow per-owner egress infrastructure. This PR changes neither host security policy nor network grants. Existing proxy allows TLS to `auth.openai.com:443` and `chatgpt.com:443`. Browser users must also be able to open `https://auth.openai.com/codex/device`. Native tool network access remains disabled. Each owner needs the existing separately approved private network/proxy and dedicated home/workspace volumes; self enrollment does not create a network.
4. Run the unchanged full protected-mask and token-bearing process probes on **that new image** on the actual host, preserving complete results. Set `PERSONAL_CODEX_NATIVE_IMAGE` to its complete immutable ID, `PERSONAL_CODEX_DOCKER_EXECUTABLE=/usr/bin/docker`, and `PERSONAL_CODEX_SANDBOX_PROFILE=collectiveui-sandbox-v1`; run `node scripts/probe-personal-codex-protected-masks.mjs` and `node scripts/probe-personal-codex-siwc.mjs`. Both must exit zero with all checks true before recording the existing sandbox gate. A failure needs review; do not loosen policies to pass it.
5. In the protected broker JSON use `backend:"docker"`, **`authenticationMode:"native"`**, the new `image`, existing protected `socketPath`/namespace/security profile, and the intended **database user ID** in `owners`. Do not use a guessed ID or change the user’s email/UPN. `allowSelfEnrollment` is optional and false by default. `siwcSandboxVerified:true` remains the historically named full sandbox readiness gate; carry it forward only after step 4. Existing SIWC deployments must explicitly choose `authenticationMode:"siwc"` when updating rather than silently switching modes.
6. Stop the old broker/runtime only after confirming no active Codex work. Update/reconcile the owner container to the new immutable image while retaining the exact owner home/workspace volumes and labels. The provisioner deliberately rejects image mismatches; it does not delete/recreate an unexpected container. Restart the updated broker with its protected config. The operator must resolve a stale broker socket rather than having the service remove an arbitrary socket.
7. Both web and worker need `PERSONAL_CODEX_SOCKET` and access to the broker’s protected Unix socket directory. Keep Docker/broker sockets out of the agent container and browser. Preserve the existing socket group/permissions and runtime receipt directory. The base release compose does not add this deployment-specific socket mount automatically.
8. Enable ChatGPT access for the intended local user in Admin → Settings → ChatGPT; allow the intended personal plan or workspace according to existing policy. No SIWC host ID or companion setting is needed for device mode. Do not change workspace restrictions just to pass login.

## Owner acceptance after approved rollout

Open Settings → Connected accounts → Stock Codex, check the consent, click Connect stock Codex, enter the displayed code on OpenAI, and return to confirm the displayed account. Use a caller-mode Codex bot with ChatGPT subscription funding and a model/effort returned by that owner’s stock runtime. Send a normal message, then ask it to create/read a harmless file in its workspace. Restart the broker/runtime and confirm the same connection and file persist; exercise a later refresh, disconnect, reconnect, cancel, and expired login. Check a second owner cannot read or use the first account. Test a workspace denied by admin policy without changing the policy.

Real login, consent and authenticated inference must be done by the owner. No real grant, credentials, token import, deployment, signing change, or production-security change was performed by this task.

## SBX prerequisites remain separate

The parent reports nested KVM already verified on the target host. That does not establish service-account access to `/dev/kvm`, working `sbx` installation/daemon, or an approved template. For an SBX test, the operator still needs official CLI **v0.48.0** at the configured path; a private broker-owned `sbxHome`; service-user KVM/daemon access; SSH forwarding disabled and empty agent socket; an imported approved immutable desktop template; a disposable boot/inspect/resource/digest proof; and the separate credential-containment and authenticated-inference checks in [computer deployment](../deploy/computer-view.md). This PR leaves SBX in explicit SIWC mode and does not claim browser device auth support there. No SBX installation or service-user permission change was performed.
