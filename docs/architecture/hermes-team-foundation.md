# Hermes Team Bot foundation

Team definitions extend `bots`, `bot_access` and `bot_user_access`; they do not create another catalog. Migration `0038_hermes_team_bots` is generated against `0037_learning_usage`, preserving native learning, its usage metadata, and all existing personal Hermes bindings and volumes. No migration enables Team Bots. The application flag `HERMES_TEAM_BOTS_ENABLED=1` must be explicitly configured for synthetic/staging work; the broker has a separate disabled flag in the subsequent runtime increment.

The foundation records maintainers, unique member user×bot profiles, one shared working admin profile, explicit conversation modes, bounded publication captures, immutable-revision storage, resource overrides/conflicts, durable operation receipts and run attribution. Maintainers must be current administrators and explicitly assigned to the bot. Instance ownership and admin oversight never substitute for a shared audience grant. Fresh user/session/bot/audience/maintainer checks protect saved contexts as well as new reservations. The working runtime owner is `team-admin:<botId>` and is never an administrator's personal owner/default profile.

Member mode also requires current personal Hermes enrollment because its private profile uses the member's personal container. Audience membership, including an administrator's audience membership, cannot bypass a denied or revoked enrollment. The trusted first-open adapter checks enrollment under the personal owner lock before issuing a personal runtime lease; Team grants cannot create or extend that lease themselves. Personal bot creation permission remains separate. The worker renews enrolled human owners and leaves reserved `team-admin:<botId>` owners to their independently checked maintainer grants.

A Team grant expiring between turns drops its capability and any never-started candidate preparation. It retains the personal lease, private profile mapping, history and unrelated personal or Team work. Expiry still stops the owned runtime when the affected Team scope has a controller, active/uncertain native candidate or retained start receipt, or when runtime maintenance prevents proving quiescence. Explicit access revocation retains the conservative runtime-wide stop and durable cleanup receipts. These server checks apply to web and compatible native API callers; no client can mint a grant or change the runtime owner.

The enrollment/lifecycle change adds no client capability: web retains its Team flow, iOS continues its web handoff, and macOS continues to disable unsupported native Team entry. Synthetic tests cover the server authority matrix and compatible API responses; installed-client acceptance and Linux container/filesystem acceptance remain separate.

Mode changes create or open separate conversations. They never reclassify private history. Members have private histories and resources; maintainers intentionally share the working profile's native skills and memory. Team transcripts cannot be shared or continued through public snapshot links. Search/sidebar views suppress revoked working contexts. Legacy activity/workspace panels return no Team content; native Team views must be supplied by the scoped runtime adapter.

Existing app connections cannot become a fallback. Direct target resolution blocks Team inference until a verified route exists; groups, delegation, routines, templates and CollectiveUI skill drafting refuse Team definitions. Generic mutation cannot change their app/direct execution/coordinator invariants. Team conversation bindings suppress app memory extraction and the native-harness utility-learning scheduler, recovery queue and worker, including jobs created before a definition changes. Native turns skip app memory embeddings and utility title inference. Hermes remains the learning engine.

Ordinary memory extraction, native-harness review and skill drafting hold the bot's shared row lock across a fresh durable Team-context check, utility work and persistence. Team conversion acquires the same bot row for update, so it must complete either before admission or after admitted ordinary work ends. Knowledge uploads check Team/native compatibility under this lock before embedding. Admitted utility calls use a 60-second abort signal without SDK retries. Knowledge uploads also serialize per bot with an advisory lock without upgrading the shared row lock.

Utility queries, saved-provider lookups, embedding configuration and accounting reuse the admission transaction. This avoids waiting for another pool connection while holding the bot lock. Accounting inserts use savepoints and are drained before the transaction ends. When memory, drafting or knowledge persistence rolls back, reported usage is replayed after rollback from a bounded buffer using stable event IDs; replay does not duplicate a previously committed event. Failed native-harness reviews commit their bounded attempt counter and accounting before rethrowing, while failed learning writes roll back their savepoint.

## Validation and enablement boundary

`tests/unit/hermes-team-store.test.ts` executes the complete migration journal in disposable embedded PostgreSQL with synthetic users. It covers repeated/concurrent reservations, different users, separate admin contexts, fresh admin and maintainer permissions, audience revocation, disabled flags/definitions, session expiry, retained mapping protection, stale edits, old company-app/group fallback refusal, private saved contexts, durable native-learning guards and revoked search/sidebar previews. No production database, credentials, OAuth, inference or container is used.

`hermes-team-learning-fence.test.ts` races conversion against utility admission, checks zero provider calls when conversion wins, and preserves ordinary learning after successful admission. It exercises structured-output and database-write failures with accounting retained and partial learning discarded. `llm-utility-transactions.test.ts` uses real saved-provider resolution, SDK mock models and embedded PostgreSQL, forbids global queries during admission, and verifies ledger savepoints and replay. Existing native-harness learning regressions remain covered by `native-learning.test.ts`. Retained Team definitions also block the native learning curator, usage metadata and preference/revision reads even when legacy bot fields change. The curator locks the bot before its lesson and any metadata write. `hermes-team-foundation-upgrade.test.ts` verifies fresh and 0035/0036/0037 upgrades through 0038 with the actual Drizzle ledger, preserved personal/runtime/history/learning rows, replay and rollback recovery. The PGlite fixture substitutes unsupported vector execution SQL; real PostgreSQL/pgvector and native-volume upgrade evidence remain separate.

The foundation remains behind default-off gates. Later increments implement [native resource capture/publication](hermes-team-publication.md), [private updates](hermes-team-member-updates.md), [candidate model/tool handlers](hermes-team-candidate-adapters.md) and [active native startup/learning](hermes-team-active-runtime.md). Their production verification inventories remain empty, so these implementations do not make ordinary Team inference or a live pilot available. See [verification gates](hermes-team-pilot.md).
