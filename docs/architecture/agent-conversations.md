# Agent-centered conversations

Selecting a bot (sidebar, directory, search, details or model picker) opens its **home chat**. The bot roster keeps a stable alphabetical order within the existing pinned/hidden groups. The chat header and bot options offer **Start side chat** for focused work and **Chat history** for earlier conversations, routine results and archives. Ordinary app/model chats and group chats keep their existing behavior.

The active home is selected in the bot roster, including `aria-current="page"`, without a duplicate entry in ordinary dated history. An opened bot beyond the five-row limit, or an explicitly hidden bot opened directly, is temporarily shown without changing its preferences. Side chats and homes retired by `/new` remain in dated history and select their own conversation row. Explicit pinned/project shortcuts and history for unavailable bots remain accessible. Home archive/delete controls are in the header's history menu.

## Identity and lifecycle

`conversations.is_bot_home` marks a canonical home. A partial unique index on `(user_id, bot_id)` arbitrates competing opens across tabs and web replicas. `openBotHome` performs a transactional UPSERT that returns the existing ID without changing its title, leaf, messages or activity timestamp. User and bot row locks serialize disable/delete/visibility updates with opening; each request authorizes the signed-in principal against the current bot visibility and group grants. Admin access creates an admin-owned home, never opens somebody else's transcript. This repository has one organization per installation/database; there is no organization ID or tenant-routing input. A future multi-tenant schema must add the tenant to all ownership/access rules and this key.

Migration **0010_bot_home** defaults existing rows to false. No old chats are adopted, merged, moved or deleted. Archiving a home clears the marker atomically and keeps its messages accessible through bot history and Settings → Archived chats. The next bot selection creates a fresh home. Unarchiving an old chat does not displace the new home. Explicit delete retains existing delete semantics. Deleting a bot clears the conversation's bot FK and preserves its transcript. Disabled, deleted or revoked bots cannot open a new home or take another turn; owned saved transcripts render with sending disabled. An inaccessible target no longer falls through to a default app.

`/new`, `/reset`, and **Chat history → Start fresh home** rotate a bot's home atomically. The former home becomes an ordinary chat with `archived=false`, dated now so it remains under Today. The replacement is the canonical home. Messages, branches, long-term memory, approvals and provider profile files are not cleared. From an ordinary side chat these commands create another ordinary chat, without changing the home.

The `home_successor_id` receipt makes simultaneous requests and retries from an old home return the same first successor, including attempts with different proposed IDs. It is deliberately not a foreign key: deleting the successor leaves a receipt that returns a clear conflict instead of silently rotating again. A retry can return a successor that has itself since been retired; selecting the bot always resolves the current home. Existing destination IDs cannot be adopted as a home. Side-chat creation also uses a retry ID and checks ownership and target after conflict.

Rollover takes the same per-user advisory lock as run admission and approval continuation, then locks the source row. Queued/running/waiting runs, legacy approval cards without a durable run, and unconfirmed Hermes cancellation block rollover with no identity or transcript changes. If rollover wins a race with admission from a stale home snapshot, admission returns 409 before inserting its message/run. A missing source that was already resolved by the request returns 404. Deliberately reopening retired history still allows normal conversation behavior.

The canonical ID is a UI identity, not a provider session identity. It does not enlarge context windows, add compaction, or combine histories. Durable run IDs, message trees, branching, approvals, replay, routine delivery to the inbox, per-user/per-bot memory and shared user memory are unchanged. Bot history is owner-filtered and paginated; the sidebar retains its existing 500-chat window and search remains available for older chats.

Saved chat entry loads an owner-authorized, uncached `/api/chat/[id]` snapshot before mounting the composer. A repeatable-read database transaction reads its leaf, message rows and active run together. Its authoritative summary also synchronizes the sidebar's current identity, even for a newly created home or a conversation outside the sidebar's 500-row window. Partial streaming updates cannot invent a placeholder chat with missing bot/home metadata. This avoids restoring an empty/stale App Router page snapshot on Back/Forward; sidebar revalidation does not remount or interrupt the current stream. The extra request is a navigation cost. As before, the full saved message tree is loaded, so very large homes can increase load time.

## Activity and outputs

The right-hand panel keeps the bot card and routine editor. Activity includes queued/running/waiting runs, failed/interrupted runs only when they are the latest attempt in their conversation, and succeeded routine/background runs. Ordinary completed replies and cancelled runs stay out of this work list. Approvals appear first, followed by active work, latest failures, then completed work; the display is capped at ten entries. Separate scoped aggregates calculate working/approval state over all open runs, so the row limit cannot make the bot incorrectly appear idle. Routine names and background labels identify the kind of work. Queries require both the run's and conversation's user/bot IDs to match the current principal and bot. Admins do not gain access to another person's activity.

Outputs contains only resolvable local files referenced by assistant messages from succeeded runs (or pre-run legacy messages), owned by the same user. Plain assistant text, unfinished/failed results, foreign file IDs, and files also referenced in the user's input messages are excluded. Files are deduplicated and eligibility is applied before the ten-file limit, so later text replies cannot bury older file results. Links use the existing authorized download route. There is no general artifact registry; workspace/tool results without a persisted attachment reference do not appear, and the panel shows an honest empty state. Both sections poll every ten seconds while visible, with empty/error/retry states, a desktop collapse control, and a keyboard-dismissible mobile dialog. Existing transcripts, routines and Inbox delivery are unchanged.

## Provider behavior

- Native API providers and OpenAI-compatible models retain the existing selected-branch replay and model context limits. A growing home transcript can eventually hit those limits; this change adds no automatic summarization or compaction.
- ChatGPT plan apps retain the person's credentials, conversation-scoped request behavior and sealed-reasoning replay restrictions. Changing UI navigation does not share a provider session with side chats or another user.
- Hermes retains its existing **one Hermes session per portal conversation**: `sessionId` includes the conversation and bot IDs (`portal-${conversationId}-${botId}`); the connection's `sessionKey` remains scoped to the app and signed-in user. Home, side and rolled-over home chats have distinct session IDs. Hermes owns its tools, model and profile memory; users of a shared profile still share that profile's memory and skills. This pre-existing profile scope is not narrowed by a home chat. A valid, allowed per-chat model preference follows `/new`; profile defaults do not change. Approvals, stops, durable runs and other scoped slash controls retain their existing integration.

[Hermes Bot Mode](https://hermes-agent.nousresearch.com/docs/user-guide/bot-mode) documents a permanent Bot Chat reached by selecting a bot, with ordinary sessions beside it. Its canonical chat redirects `/new` and `/reset` to compaction and its archive reachability differs from this portal. CollectiveUI implements the navigation pattern but intentionally rotates its local home on those commands; it does not request Hermes Desktop's canonical Bot Chat or compaction protocol. [Muse's design article](https://introducing.muse.ai/) describes a main ongoing conversation and side chats for separate topics. These are product references, checked 2026-10-01, not assumptions that their backend protocols match this repository.

Native mock-provider browser tests and the existing mock Hermes gateway tests validate local behavior. A deployed Hermes profile, external model context exhaustion, and profile-memory behavior on a production gateway still require environment-specific verification. No live provider connection is required by this migration.
