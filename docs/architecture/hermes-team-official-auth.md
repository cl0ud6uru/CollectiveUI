# Dormant official plan authorization candidate

This increment builds the authorization protocol around the separate official plan account introduced in migration0044. Migration0045 adds owner/session-bound sign-in attempts and one-shot refresh/revocation receipts. It does not enable authentication or model routes.

Migration0048 adds a dormant [protected VM transfer and workspace provenance candidate](hermes-team-work-connections.md). The exact local-tool/secure-transfer adapter remains unverified; a literal workspace identifier is unnecessary for per-registration isolation, while a corporate-workspace allowlist would require separately verified evidence; production connection and model inventories are still empty. The transfer candidate is separate from the synthetic loopback-return interface below.

The server account controller is `GET/POST /api/account/official-plan`. Status contains no account subject, host, client, token, catalog or filesystem identity. Mutations use current CollectiveUI authentication, strict JSON action bodies and the existing same-origin check. Production connect, reconnect, refresh and remote disconnect remain unavailable because `VERIFIED_OFFICIAL_LOOPBACK_TRANSPORTS` is empty. The connection UI continues to report `connectAvailable:false`.

`OfficialLoopbackTransport.prepare` is the integration boundary. It must establish an authenticated local listener before returning its stable host and exact callback URI. The authorization URL contains fresh state, nonce and S256 challenge. The verifier is encrypted in a v2 owner/session/attempt-bound envelope; the return bearer is delivered only to that trusted transport and stored as a hash. `officialPlanReturnHttp` accepts an authenticated adapter return, not an OpenAI HTTPS redirect or a pasted authorization code. It is deliberately unregistered as a public callback route.

The callback claims a durable attempt before code exchange. Only the callback's issued registration may exchange an initial dynamic registration. Its documented optional scope field is bounded metadata; token-response and signed access-token scopes determine permission. Reconnect retains the original registration/subject/host. JWT signature, issuer, audience, expiry, nonce, client, subject and direct-plan permission are verified before the same-token catalog is loaded. The selected account and session are checked again in the atomic storage transaction. An identical completed return is harmless; changed, expired, concurrent or uncertain returns cannot repeat the exchange.

Refresh claims one receipt per account credential revision before any external request. A successful rotation replaces the encrypted bundle and account-specific catalog together. Unknown I/O, a lost acknowledgement or an interrupted receipt pauses every subsequent model purpose and refresh attempt for that credential revision. Reconnect obtains a new verified revision instead of repeating an uncertain rotating token. Local disconnect clears the secret first. Remote confirmation requires the documented empty HTTP 200 response. Other responses and accounts without a refresh grant retain an attention receipt and report confirmation as false on repeated disconnect, without repeating network I/O.

The optional `earliest_refresh_at` hint is retained as bounded opaque private data. The published contract does not define its format/units; this candidate does not infer a schedule from it or multiply it as a presumed Unix timestamp. Refresh is an explicit owner operation. Automatic refresh scheduling remains gated on a verified timing contract.

Both token and discovery responses have byte/time bounds, fixed HTTPS origins and redirect rejection. The JWT candidate supports RS256 with bounded public RSA keys and no JWT-supplied key URL; a future discovery using another algorithm is explicitly unsupported. The pure verifier is compatible with standalone Node workers and has no Next-only import marker. No provider cost or hard token ceiling is inferred from successful sign-in.

The primary contracts were read on2026-10-07: [official loopback registration/sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [account refresh/revocation](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [access token claims](https://developers.openai.com/siwc/token-sharing-open-source/token-reference), and [OIDC discovery/signature validation](https://developers.openai.com/siwc/website). The website identity registration is a separate integration and is not silently substituted for plan permission.

Offline fixtures use synthetic owner accounts, generated signing keys, disposable PGlite and injected HTTP responses. They cover actual callback-to-signature-to-storage ingestion, PKCE, nonce/client/owner/session checks, callback replay, crashes, unknown rotating refreshes, private metadata, local revocation, time/byte bounds and canonical migration preservation. No listener, OpenAI grant, account credential, model inference or deployment is used during these tests.

The return interface is a synthetic protocol boundary, not an implemented or verified remote sign-in integration. A local listener alone does not complete it: the documented [self-hosted VM flow](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) completes OAuth on the browser's machine, then securely transfers the selected registration's protected credential file while preserving the VM's separate host ID. It does not document forwarding a callback code to this server for exchange. A supported implementation needs the same trusted tool/client and selected user/workspace, an authenticated owner-bound import destination, distinct origin/VM host provenance, and one owner of refresh/rotation across copies; this increment supplies none of those transfer operations. An officially supplied registered web-client plan-usage contract would be another integration, separate from website identity sign-in.

Transferred sessions currently lack provider host-specific usage attribution and host-specific plan revocation. The application actor/run ledger is application attribution; local disconnect revokes local access, and refresh-token revocation concerns the renewable session and may affect other copies. Neither is evidence of provider host-only revocation. Production inventories remain empty. Subsequent live verification separately needs approval for a synthetic account grant, a supported connection/import path, account-specific model entitlement/catalog, all four native purposes, expiry/rotation and actual usage attribution. Public HTTPS callback and paste-return alternatives are not invented.
