# Native Hermes workspace inspection

This follow-up to the native remote workspace adds **Workspace panels** at `/hermes/[connectionId]/operations`.

- Projects: native `projects.list`, including archived state and non-sensitive workspace folders. A selected, owned and idle native chat may prepare explicit, confirmed creation of an **empty inactive** project, or explicit selection of a non-archived project returned by the refreshed native list. The server generates project slugs and sends `folders: []`; the browser cannot submit paths or project identities that Hermes has not listed.
- Workspace files: an exact-pin opt-in native `collective.workspace.files` extension lists directory entries and reads bounded UTF-8 text. A separately versioned `collective.workspace.files.write.v1` method edits an existing small UTF-8 file only after an explicit two-step confirmation. The edit binds the selected chat, profile, workspace ID, relative file path, previously read content digest, and edited-content digest; Hermes rechecks the old digest immediately before atomic replacement, then the portal reads the file back before reporting success. Receipts prevent replay after ambiguous outcomes. It cannot create, rename or remove files. Both methods are available only for the selected saved chat's attached, idle session when its persisted explicit local cwd falls under an unarchived project folder in that profile's native `projects.db`. A missing or ineligible project returns unavailable; the portal never substitutes a process cwd or caller-supplied root.
- Schedules: profile-proven native `cron.manage` list for the selected profile, including enabled state, native lifecycle state, schedule and next-run metadata. Prompts, commands, delivery credentials and execution output are omitted. An idle selected chat may prepare explicit, confirmed pause only for a currently scheduled job, and resume only for a paused or recoverable-error job. Completed jobs have no resume control and are rejected server-side, because Hermes resume can re-arm finite schedules. Resuming warns that it may run soon and use model usage. The native response must prove profile scope and the requested state is read back before success.
- Plugins: read-only `plugins.manage` list, with `plugins.list` fallback only when the newer method is unsupported. Configuration, schema values, server credentials and installation paths are omitted.
- System: bounded version, architecture, CPU, memory, disk and uptime fields from `/api/system/stats`. Hostnames, process identity, paths, environment values and raw config are omitted.

Every request requires the signed-in portal principal, an owned connection, the organization admission flag and a profile from the authenticated dashboard roster. Project and schedule mutations additionally bind an encrypted, short-lived confirmation to the owner, connection, server-owned chat/runtime/profile, and current socket epoch; they require an idle chat with no queued work or prompts. A durable one-shot receipt is written before dispatch, duplicate confirmations are never replayed, and resulting state is read back from Hermes before success is reported. Creating an empty project is separate from activating a project. Project selection and schedule pause/resume affect the whole native profile, so confirmation explains the profile-wide effect.

Profiles select native data within the dashboard account; they are **not portal tenant security boundaries**. Plugin and system panels describe the shared Hermes instance. This feature is for personal remote connections; managed/local and admin-shared backends require their own authorization and isolation integration.

HTTP routes and RPC methods are fixed server-side. Callers cannot provide arbitrary endpoints or methods. Existing pinned transport, redirect restrictions and encrypted server-owned credentials remain in use. JSON responses are limited to 1 MiB, projected rows to 500 and strings to bounded display lengths. Native errors are translated into generic panel errors without forwarding upstream response bodies.

Workspace file access is implemented by a separately installed exact-pin native extension, not by forwarding the dashboard's `/api/fs/*` routes. The installer validates the pinned source and composes #247 recovery → #95 workspace method registration → #96 owner fence; the new method must exist before the owner fence snapshots its method table. This repository change only validates that composition; it does not apply the installer, create a workspace grant, or restart Hermes.

The native methods derive their root from the persisted session cwd and an unarchived project folder in the bound profile's native `projects.db`. They require the full owner/transport binding, the currently attached session, idle/no-queue/no-delegation state, and the effective terminal backend `local` (including `terminal.backend` configuration when `TERMINAL_ENV` is unset). They reject process or settled cwd fallbacks, paths outside the registered project, exact filesystem, shared temporary/mount, and home roots plus protected system subtrees, symlinks, traversal, hidden and sensitive/token names, non-regular files, hard-linked files, and different-device descendants. Exact broad roots such as `/tmp`, `/mnt`, and `/private` are rejected; a specific registered child such as `/private/tmp/myrepo` is considered only after all other project/session authorization checks pass. On systems where `/tmp` is a canonical directory, a registered `/tmp/myrepo` child is treated the same way. Directory listings are capped at 100 entries (1000 scanned); reads and writes are capped at 256 KiB and accept UTF-8 text only. Descriptor-relative no-follow opens protect path traversal and replacement races. Edits compare the expected digest again immediately before rename and verify the saved bytes. The filesystem does not offer a portable hash-conditioned rename, so an unrelated out-of-band writer racing the tiny interval between final digest check and atomic rename cannot be excluded by this protocol. Same-device bind mounts are not independently distinguished from ordinary directory entries; these are documented residual boundaries, not claims of full filesystem isolation.

Optional endpoints missing on older Hermes versions show an unavailable-panel error. The project browser falls back to the native working directory if `projects.list` itself is unsupported. No new database migration or runtime credential is required beyond the native remote connection prerequisites.

The project and schedule RPC capabilities are established by the pinned Hermes desktop contract (`f97608f178d1ffeca59860195ab7da295f7c8e5f`) and probed on the current socket with `projects.list`, exact-target `projects.get`, and profile-scoped `cron.manage` list; unsupported or unscoped methods fail closed. The visible project list is capped at 500 rows, but creation and duplicate reconciliation use `projects.get` on the server-generated slug (and final readback uses the returned native ID), so a valid result beyond that UI window is not reported as uncertain merely because it is not displayed. The targeted raw result is used only for exact ID/name/slug and empty-folder validation; it is never returned to the browser, and privacy-filtered folder lists are not treated as authoritative proof of emptiness. This increment does not add folder attachment, project editing/archive/deletion, file creation/removal/rename, schedule creation/removal, plugin toggles/install/uninstall, or discovery-policy changes.

The composed regression harness exercises read/list and the versioned write endpoint through the pinned Hermes dispatcher, native contract validation, and the current published #266 owner wrapper. Its write cases cover successful replacement/readback, stale digest, unknown contract fields, unclaimed/foreign/busy/non-local requests, replaced ownership, and protected or nonexistent paths. The session idle check and filesystem operation share the native history lock so a background notification turn cannot start between review and file access. A concurrency regression using the actual pinned native admission helper fails before this lock is held and passes after it is held. The harness uses synthetic server/session/profile state; full-gateway integration and independent acceptance of the owner adapter remain held. No owner implementation or service is changed by these tests.
