# Native Hermes workspace inspection

This follow-up to the native remote workspace adds **Workspace panels** at `/hermes/[connectionId]/operations`.

- Projects: native `projects.list`, including archived state and non-sensitive workspace folders. A selected, owned and idle native chat may prepare explicit, confirmed creation of an **empty inactive** project, or explicit selection of a non-archived project returned by the refreshed native list. The server generates project slugs and sends `folders: []`; the browser cannot submit paths or project identities that Hermes has not listed.
- Directories: native dashboard default working directory and project folders, followed by read-only `/api/fs/list`. Directory names are visible; file contents, downloads and filesystem mutations are unavailable.
- Schedules: profile-proven native `cron.manage` list for the selected profile, including enabled state, native lifecycle state, schedule and next-run metadata. Prompts, commands, delivery credentials and execution output are omitted. An idle selected chat may prepare explicit, confirmed pause only for a currently scheduled job, and resume only for a paused or recoverable-error job. Completed jobs have no resume control and are rejected server-side, because Hermes resume can re-arm finite schedules. Resuming warns that it may run soon and use model usage. The native response must prove profile scope and the requested state is read back before success.
- Plugins: `plugins.manage` list, with `plugins.list` fallback only when the newer method is unsupported. An idle selected chat may prepare a confirmed enable/disable for a currently listed user-installed plugin using its exact, unique canonical key. Mutations require a complete inventory within the 500-row verification bound; legacy rows, bundled plugins, ambiguous/malformed identities and unsupported states remain read-only. Enabling can activate tools, skills, commands and hooks in the profile's running gateway and open chats; disabling updates profile settings but does not immediately unwind handlers, so a restart may be required. The result reports the native gateway reload status, and success/readback is tied to the same plugin key, name and user-installed source. Configuration, schema values, server credentials and installation paths are omitted.
- System: bounded version, architecture, CPU, memory, disk and uptime fields from `/api/system/stats`. Hostnames, process identity, paths, environment values and raw config are omitted.

Every request requires the signed-in portal principal, an owned connection, the organization admission flag and a profile from the authenticated dashboard roster. Confirmed project, schedule and plugin mutations bind an encrypted, short-lived confirmation to the owner, connection, server-owned chat/runtime/profile, and current socket epoch; they require an idle chat with no queued work or prompts. A durable one-shot receipt is written before dispatch, duplicate confirmations are never replayed, and resulting state is read back from Hermes before success is reported. Creating an empty project is separate from activating a project. Project selection, schedule pause/resume and plugin enable/disable affect the whole native profile, so confirmation explains the profile-wide effect.

Profiles select native data within the dashboard account; they are **not portal tenant security boundaries**. Plugin and system panels describe the shared Hermes instance. This feature is for personal remote connections; managed/local and admin-shared backends require their own authorization and isolation integration.

HTTP routes and RPC methods are fixed server-side. Callers cannot provide arbitrary endpoints or methods. Existing pinned transport, redirect restrictions and encrypted server-owned credentials remain in use. JSON responses are limited to 1 MiB, projected rows to 500 and strings to bounded display lengths. Native errors are translated into generic panel errors without forwarding upstream response bodies.

Directory roots come from native working-directory/project metadata. The portal rejects hidden/sensitive paths, traversal, non-normalized paths and paths outside those roots. Each ancestor must appear as a real directory in a native parent listing; symlink leaves and invented descendants cannot be selected. Native root authorization and symlink behavior remain the remote dashboard's responsibility. Directory browsing is metadata-only and is not a filesystem sandbox.

Optional endpoints missing on older Hermes versions show an unavailable-panel error. The project browser falls back to the native working directory if `projects.list` itself is unsupported. No new database migration or runtime credential is required beyond the native remote connection prerequisites.

The project and schedule RPC capabilities are established by the pinned Hermes desktop contract (`f97608f178d1ffeca59860195ab7da295f7c8e5f`) and probed on the current socket with `projects.list`, exact-target `projects.get`, and profile-scoped `cron.manage` list; plugin list/toggle use the exact `plugins.manage` methods and canonical key contract under the server's pinned profile-scope wrapper. Unsupported or unscoped methods fail closed. The visible project list is capped at 500 rows, but creation and duplicate reconciliation use `projects.get` on the server-generated slug (and final readback uses the returned native ID), so a valid result beyond that UI window is not reported as uncertain merely because it is not displayed. The targeted raw result is used only for exact ID/name/slug and empty-folder validation; it is never returned to the browser, and privacy-filtered folder lists are not treated as authoritative proof of emptiness. This increment does not add folder attachment, project editing/archive/deletion, arbitrary file-content access or editing, schedule creation/removal, plugin installation/update/removal/settings, bundled plugin toggles, or discovery-policy changes. Directory views remain metadata-only and do not claim to be a filesystem sandbox. Those operations need separately reviewed capability and workspace-authorization designs. Native root authorization and symlink behavior remain the remote dashboard's responsibility.

Validation:

```sh
npx vitest run --configLoader runner tests/unit/remote-hermes-operations.test.ts tests/unit/remote-hermes-projects.test.ts
node tests/browser/remote-hermes-operations.mjs
npm run typecheck
```

Unit checks cover ownership/admission, profile validation, secret-free projections, hidden paths, directory ancestry and symlinks, fixed read-only directory transport, response bounds and unsupported-version errors. Mutation tests cover path-free empty creation, server-listed selection with exact native readback beyond the 500-row display window, hidden-folder empty-project rejection, scoped schedule pause/resume, completed-job no-replay, exact-key non-bundled plugin toggles, ambiguous or changed plugin identity, profile matching, busy/uncertain session gates, fresh readback, one-shot receipts, concurrent duplicate reconciliation and ambiguous outcomes. Synthetic browser fixtures verify explicit two-step project, schedule and plugin confirmations, completed-job control suppression, shared-profile warnings, schedule-resume and plugin activation/restart guidance, all five panels and dynamic session navigation. They do not replace validation against a live dashboard.
