# Personal Remote Hermes commands

This applies to the native dashboard workspace at `/hermes/[connectionId]`, using JSON-RPC over a server-owned WebSocket. App/bot chats using the Runs HTTP API retain the separate [bounded chat controls](hermes-slash-commands.md). PR52's request fix and PR71's model picker do not establish native remote parity or deployed behavior.

Previously, the workspace displayed the raw command catalog and sent every leading slash to `slash.exec`. Upstream catalogs contain `pairs`, `canon`, `commands` metadata and a `skills` map. Known skills reject `slash.exec` with `4018` and require `command.dispatch`. Other `4018` errors can follow side effects, so they are not a general retry signal.

| Command/surface | Official Hermes | CollectiveUI native remote |
| --- | --- | --- |
| `/help`, `/status`, `/usage`, `/version`, `/tools`, `/toolsets`, bare `/skills` | Native commands; some are CLI-only on messaging platforms | Catalog-gated native execution, idle only; no arguments |
| `/compress` (`/compact`), `/title [text]` | Native session operations | Catalog-gated native execution, idle only |
| `/<installed-skill> [task]` | Native skill expansion | Advertised skills prepare an unsent draft; human review and Send are required |
| `/commands` | Messaging command, hidden from dashboard catalog | Readable catalog and searchable menu |
| `/context` (`/ctx`), `/stop` | Native context/interrupt controls | Fixed context/interrupt RPCs, including while running |
| `/yolo [status|on|off]` | CLI/gateway toggle session approval bypass; native TUI has an explicit session setter | Status panel and explicit on/off confirmation; idle only, verified runtime, administrator gate off by default |
| `/approvals [status]` | Setters persist profile-wide approval policy; gateway setters recheck slash administration authority | Status only; profile-wide setters unavailable. Pending prompts offer Allow once and Deny |
| `!yolo`, `!<shell-command>` | CLI shell syntax; `!yolo` attempts a shell executable named `yolo` | Explicitly refused; never sent to inference or executed as shell |
| `/steer`, `/queue` | Native active-turn controls | Existing Steer / Queue buttons; slash variants deferred |
| `/model`, `/reasoning`, `/personality`, `/new`, `/reset`, `/undo`, `/retry`, `/fork`, `/resume` | Native session/configuration controls | New Hermes chat button remains available; additional slash adapters deferred |
| Config, plugins, cron, quick exec/aliases, gateway lifecycle, terminal UI | Interface-specific and/or profile-wide | Unavailable in chat commands; use dedicated authorized settings or native Hermes |

The menu explains unavailable entries. Choosing a command only edits the draft; keyboard completion selects runnable matches. Supported aliases resolve through the current catalog. Whole-token parsing preserves paths/prose; `//help` sends literal `/help`. Command attempts with attachments preserve both files and text.

## Confirmed session YOLO

YOLO mutation is technically supported at both checked revisions. Prior status-only behavior was a product allowlist restriction, not an upstream limitation. Native administration continues to accept `reasoning` and `fast`, and pending approval replies remain `once` and `deny`. YOLO now has a separate, narrowly validated endpoint. Admin → Settings → Personal remote Hermes adds **Allow confirmed session YOLO changes**, off by default, including for existing settings rows. The audited administrator action controls this gate; the owned conversation's signed-in user confirms each mode change. No deployment setting is enabled by this implementation.

`/yolo` opens status and explicit on/off choices; `/yolo on|off` prepares the exact requested change. Choosing a state issues an encrypted server confirmation bound to owner, connection, persisted/saved/runtime conversation identities, verified socket epoch, profile, explicit value, unique receipt and a one-minute expiry. Only the subsequent **Confirm session YOLO ON/OFF** action dispatches. Cancellation and conversation switching discard the browser confirmation. Ordinary drafts and attachments are retained when using the header control; an unchanged initiating slash draft clears after success.

Ownership, authenticated profile access, both administrator admission gates, runtime compatibility and idle state are checked again on confirmation. Settings/session locks recheck identity and admission immediately before dispatch; cached identities are checked as well because native events can precede database updates. Active turns, pending prompts, queued work and uncertain outcomes are refused. A durable receipt precedes dispatch and prevents confirmation replay, including after a lost acknowledgement. Only `config.set` with server-owned `profile` and `session_id`, `scope: "session"`, `key: "yolo"`, and `value: "on"|"off"` is sent. No slash-worker, omitted-identity, global/profile or environment fallback is allowed. Definitive method-not-found/stale-session rejections release admission; ambiguous outcomes remain uncertain.

Mutation compatibility is deliberately restricted to session-reported Hermes **0.21.5**, native desktop contract **8**, and a matching native profile. This is the released identity verified at the native source pin; current upstream's setter/guard was also executed separately. Unknown, older, newer or modified version identities retain status inspection and an unavailable explanation until their contract is verified. Catalog presence alone is insufficient: missing-session branches on unverified runtimes can change process environment. Snapshot compatibility is bound to the socket epoch that supplied it; the setter refuses a disconnected or different socket without reconnecting. Reconnection requires fresh verification and confirmation. Both checked revisions reject a nonempty stale session ID before the setter. `config.set(key="yolo", value="status")` is not a read: unrecognized values toggle. Status is read from the session snapshot.

After mutation, a refreshed snapshot and persistent indicator show effective bypass. Upstream `info.yolo` combines session YOLO, profile `approvals.mode: off`, and process `--yolo`; disabling the session flag can leave effective bypass on. The result explicitly distinguishes that from restoring all prompts. Session scope affects every native client sharing that saved conversation; computer-use dependent resources can also change permission mode. The confirmation warns about both. Profile-wide `approvals.mode` changes require a separate administration surface; owning a CollectiveUI connection does not prove exclusive ownership of its Hermes profile. Hermes hardline/deny rules and CollectiveUI authentication, ownership, origin and admission checks remain mandatory. CollectiveUI agent `ToolSettings` filters do not run in this external native runtime, so this adapter does not claim to enforce those policies for remote tools.

CollectiveUI serializes its own admission and checks observed native idle/identity state. Other native clients can race those checks: upstream's setter has no atomic expected-session-key or idle condition. The UI cannot lock those clients; it warns that the shared conversation can change elsewhere. A stronger cross-client guarantee requires an upstream conditional setter.

Ordinary command support is detected from the authenticated catalog and method responses. Missing/malformed catalogs leave local controls available and withhold native execution. Catalog warnings also withhold native/skill execution because incomplete extension discovery cannot establish routing. Known quick/plugin collisions are refused; raw discovery warnings and quick-command bodies are not exposed. YOLO additionally requires the verified identity above.

Ownership, profile/runtime identities and admission are resolved server-side. Existing write-ahead receipts precede native mutations, and final admission is rechecked under the settings lock. The browser retains request IDs after unsuccessful attempts. Only `-32601` permits method fallback; ambiguous failures remain uncertain and are not replayed. Skill/alias directives become drafts; display, notice and warning text remain visible. Human approval choices remain once/deny. Upstream dashboard profiles are not portal tenant isolation boundaries.

## Verification

`tests/fixtures/remote-hermes-command-contract.py` executes actual pinned registry/catalog, skill-routing, config dispatcher, stale-session guard and YOLO setter functions with isolated dependencies. Its JSON records source hashes and wire results, including on/off, stale rejection, no profile/environment writes and the unsafe status word. It starts no gateway, tools or provider; the same script was run against current upstream.

Unit tests cover real catalog shapes/aliases, directives, versions, discovery failures/collisions, ownership, final admission, replay receipts, ambiguous failures, active turns, approval boundaries and literal syntax. YOLO tests cover default-off gates, exact protocol, cross-owner/target/token refusal, expiry, cached-only identity rotation, active/pending/queued/uncertain state, final disablement, definitive rejections and lost acknowledgements. The actual workspace component is exercised on desktop/mobile with synthetic HTTP for menu/keyboard, typed commands, files/drafts, skill prefills, errors, repeat actions, receipt reuse, active controls and literals, plus YOLO cancellation/expiry, inherited bypass, gated runtimes and draft/file preservation. The existing workspace browser regression covers history, uploads, prompts, queue, disablement, profile switching and stale responses.

No live runtime, credentials, policy change or deployment is used. This does not establish full native slash parity or deployed status.
