# Automatic Hermes profiles

This opt-in implementation creates a blank Hermes profile on the first direct message to a managed bot. The durable identity is **CollectiveUI user × bot**, not the shared bot owner. `/new` archives the old portal home conversation and starts a fresh native session in the **same profile**. Long-term memory and the old transcript remain. Existing native engines and manually configured Hermes Runs apps keep their existing paths.

## Operator prerequisites and supported scope

Hermes is [single-tenant; whole-process OS isolation is the security boundary](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/SECURITY.md#2-trust-model). Profiles and session keys do not isolate users. In particular, session search and other in-process code can access other profiles within the same filesystem envelope. Distinct URLs or API keys on one shared host filesystem are insufficient.

Before enabling a user, the operator must:

1. Supply a separate whole Hermes process tree, filesystem, environment/credential scope, and network policy for that user. Profiles for that user's bots live inside this boundary. External-memory providers must likewise use user-specific accounts/namespaces. Bots belonging to the **same** user are not adversarially isolated from each other.
2. Keep dashboard administration, its token, and its process namespace outside the agent's reach. A terminal-only sandbox does not meet this requirement. Use a separately protected management plane with access to the intended user's profile home; the agent must not be able to inspect its environment/processes or reach its control listener. Never mount a host Docker socket into CollectiveUI or a runtime for this feature.
3. Run the pinned dashboard and a compatible multiplexed Runs gateway, expose both to CollectiveUI through separate operator-controlled `http://127.0.0.1:<port>` listeners/tunnels, and ensure every web/worker instance sees the **same** listeners. Binding loopback inside different web/worker containers without equivalent tunnels is not sufficient. Exact destinations are registered by an admin; DNS names, redirects, URL credentials, paths, low ports, metadata and non-loopback hosts are refused.
4. Supply the dashboard session token, the selected provider's API key, and a distinct operator-created profile API key for every allowed profile slot. The runtime must allow the selected model/provider. The supplied provider key is installed into each newly created profile by the adapter; credentials are never copied from another profile. Supported providers are `openai`, `anthropic`, and `openrouter` using their documented environment-key names. Other providers/auth flows require a separately tested adapter.
5. Configure CPU/memory/process/storage/inference budgets and network isolation externally. The portal's profile-slot quota and existing per-user run cap are admission limits, not OS resource or cost isolation. Hermes' own concurrency cap is not tenant isolation.

**This implementation registers trusted endpoints and writes profile configuration. It does not create containers, establish tunnels, set up isolation, install Hermes, or install real credentials during development/testing.** Isolation/source-pin attestations are operator assertions; CollectiveUI cannot prove a remote filesystem/container boundary or source SHA from an HTTP health response.

### How loopback reaches an isolated runtime

`127.0.0.1` is relative to the CollectiveUI web/worker network namespace, not the user's remote machine. The supported topology is an **operator-established, authenticated port forward** from each registered portal loopback port to the intended user's dashboard or Runs listener. The dashboard end must run in its protected management namespace with `auth_required: false`; its token gate remains enabled. A protected sidecar or reverse proxy may provide this forwarding only if it preserves that exact contract and is inaccessible to agents. A generic remote dashboard behind cookie authentication does not become compatible simply because a proxy listens on localhost.

The adapter implements the HTTP client for this topology; it implements **no tunnel, sidecar, proxy, container, firewall or credential-delivery service**. The operator must arrange matching ports for all web/worker instances, authenticated/encrypted transport across hosts, trusted proxy configuration (bypass environment HTTP proxies for these loopback origins), and isolation of the dashboard's processes, token and listener from the agent's entire process tree. An upstream loopback bind by itself does not protect a dashboard from an agent sharing that network/process namespace. If the operator cannot provide this separation, leave managed provisioning disabled.

This topology follows the pinned dashboard's [loopback Host validation](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_server.py#L597-L621): loopback Host names are accepted when bound to loopback, irrespective of the forwarded port. Its [token gate](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_server.py#L697-L715) is authoritative only when remote cookie authentication is inactive. This is source-backed compatibility reasoning, not a validated deployment recipe; isolated live conformance is still required before activation.

The provider and profile Runs keys are intentionally installed inside that user's runtime. They are not secrets from code with access to that runtime. **The dashboard administration token must remain outside it**, must differ from all provider/profile keys, and is never written into a profile. Do not reuse provider credentials across users when the intended boundary requires per-user credentials or budgets.

Managed mode initially supports direct bot chats only. Group, delegated and background/routine execution fail closed. Skills start explicitly empty (`no_skills: true`, no hub installs/external skill directories), while toolsets are selected explicitly by the admin. No MCP servers are copied or installed. Hermes may learn skills later within its user's own boundary. Clean [profile distributions](https://hermes-agent.nousresearch.com/docs/user-guide/profile-distributions) are the conceptual template model; importing distributions or cloning existing profiles is not implemented. **Never clone a used profile**: clone behavior can carry memories, sessions, credentials or external-memory bank references.

## Admin workflow

Admin → Hermes is separate from the existing Admin → Apps manual integration. Ordinary users and agents have no management action or generic dashboard proxy.

- Register one immutable connection for an explicitly selected user. Confirm the isolation prerequisites, identify the operator boundary, select the supported protocol and enter exact `/api/health` `version` and `displayVersion` values from the pinned installation. The connection is enabled only by this explicit admin operation. Registration makes no remote call and does not claim readiness.
- Create a shared bot definition with explicit instructions, native provider/model, toolsets and empty skills. The bot/app pair is created in one database transaction. The server binds each managed app to that one approved bot (`managedBotId`). Generic create, copy and template-import flows cannot use it to authorize additional bots; create a separate approved definition in Admin → Hermes. Existing unapproved definitions fail closed until an admin explicitly selects and approves the original bot. Approval refuses conflicting retained assignments. Sharing a bot never shares another user's runtime or memory.
- Observe setup status and the lifetime slot usage. A failed profile retains its name and slot. For transient setup failures, retry by sending the preserved draft after the one-minute backoff. Identity conflicts retain a controlled operator-action diagnostic and HTTP 409; they do not suggest that retry alone repairs ownership. A lost worker's five-minute lease can be reclaimed. No retry allocates a new profile or clears memory.
- Disable a connection to refuse future requests, approvals and reconnections. Every remote call refreshes user/bot/app authorization and the connection's enabled state. Already dispatched upstream work/stream responses are not forcibly killed by a database flag; for immediate containment the operator must stop/isolate that runtime and revoke its credentials. No automatic destructive cleanup runs.
- Replace an expired dashboard session token using the dedicated write-only field. Profile/provider key replacement, raising capacity, changing endpoints, and moving users between boundaries are intentionally not generic edit operations; they need an explicit future recovery/migration workflow. Keep old encryption keys during key rotation; the worker rewraps these row-bound credentials alongside existing secrets.

Bot profile configuration is frozen once assigned. The editor rejects changes to the name, description, instructions, boundaries or app before writing anything; the profile hash also binds model/provider/toolsets. Avatar, label, starters and access settings remain editable. First-use reservation and edits lock the same bot row, then reservation locks the user's connection; the spec is reread under that lock. The editor conservatively fixes definition fields even before first use. New definitions belong in Admin → Hermes.

For an older accidentally edited definition, Admin → Hermes provides **Restore a previously assigned definition**. Supply the original name, description, instructions and boundaries from operator records. The action is admin-only, locks the bot and app, requires all retained assignments for that app to belong to that bot and match the proposed hash, then restores and approves atomically. Incorrect guesses do not change anything. The portal stores a hash, not a historical definition snapshot; without the original text it cannot reconstruct it. Conflicting prior assignments need explicit operator reconciliation; there is no reassignment or profile replacement endpoint.

Normal actions refuse deleting an assigned bot or a managed app because cancellation needs the original identity. Disable the bot/runtime instead. Conversation deletion and out-of-band record deletion retain profile reservations and remote memory; user/connection deletion is restricted while records exist. Retention/removal is an operator process, not automatic garbage collection.

## Pinned protocol

Protocol identifier: `dashboard-be5e9f72-multiplexer-v1`, source revision `be5e9f72c6681af9dfb75bf480f08844f1499949`. There is no verified stable/versioned upstream provisioning API. Registration attests to this source; exact health-version matching and response/capability checks reject drift at runtime. Upstream changes require renewed source review and contract tests.

Management uses `X-Hermes-Session-Token` with the loopback dashboard. This is `HERMES_DASHBOARD_SESSION_TOKEN` or its generated per-process value, **not** `API_SERVER_KEY`. Remote dashboard auth is not supported: remote gated deployments use cookies or explicitly endpoint-enabled auth providers, not an invented universal bearer flow. See [session-token checks](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_server.py#L364-L372) and [request authentication](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_server.py#L697-L727).

The adapter only constructs these allowlisted operations internally:

| Operation | Contract |
| --- | --- |
| Version/readiness | Dashboard `GET /api/health`; require exact registered versions and `auth_required: false`; authenticated profile roster read |
| Blank create | `POST /api/profiles`: all clone flags false, `clone_from: null`, `no_skills: true`, empty `mcp_servers`, `keep_skills`, `hub_skills`; explicit name, ownership marker, provider/model |
| Configuration | Profile-scoped `PUT /api/env` for supplied provider key, distinct `API_SERVER_KEY`, `API_SERVER_ENABLED`; profile `PUT .../model`, `PUT .../soul`; `PUT /api/config` for explicit toolsets, empty external skill directories/MCP, manual approval mode |
| Verify persisted state | Profile roster provider/model; `GET /api/config?profile=...` (**model is a flattened string**); exact `SOUL.md`; initial `GET /api/skills?profile=...` must return an empty array |
| Verify serving state | `/p/<assigned-name>/v1/capabilities`, `/v1/models`, `/v1/toolsets` using that profile's key; required Runs/SSE/stop/approval features, the assigned **profile alias** and exact configured/enabled toolsets. The native provider/model is verified separately through the dashboard. |
| Native execution | Existing Runs client, with the assigned profile target and `portal-<conversation>-<bot>` session ID; existing approval, stop, SSE and usage behavior |

Sources: [ProfileCreate schema](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_models.py#L429-L446), [create handler](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_routers/profiles.py#L803-L873), [config/env routes](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_routers/config_env.py), [config normalization](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/web_server_config.py#L529-L541), [explicit platform toolset semantics](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/hermes_cli/tools_config.py#L590-L630).

`ok: true` on creation is not success: `model_set: false` and `model_error` are handled by explicitly applying credentials/model and verifying readback. Unexpected async skill jobs are rejected. A profile not yet served by the multiplexer remains failed/retryable. The adapter never starts/restarts the gateway and never falls back to the default profile. A broken skills-discovery endpoint prevents initial readiness; update/repair the pinned deployment rather than bypassing the check.

The [pinned Runs model listing](https://github.com/NousResearch/hermes-agent/blob/be5e9f72c6681af9dfb75bf480f08844f1499949/gateway/platforms/api_server.py#L2502-L2516) advertises the active profile name and optional route aliases, not the underlying provider model ID. The adapter enables the profile API only after writing its explicit model, instructions and tool configuration; readiness also requires authenticated gateway readback. This does not prove a provider key can perform inference, and no probe runs a model or creates a native conversation.

## Persistence and failure behavior

Migration `0013_hermes_provisioning` adds `hermes_connections`, `hermes_provisions`, and a nullable `hermes_run_contexts.provision_id`. It does not adopt, clone, move or rewrite any existing manual connection/history. Manual target-key hashes remain byte-for-byte compatible.

Connection secrets use AES-GCM with row-bound AAD. Only non-secret status/metadata are projected to the admin page. Upstream HTTP error bodies are discarded; native JSON/SSE error fields are replaced with controlled messages. Known credential values are redacted from other native response strings, including within SSE frames split across transport chunks. JSON reads are capped at 256 KiB and SSE frames at 256 Ki characters; remote operations have deadlines and refuse redirects. Canonical profile paths reject normalized traversal, encoded slashes, queries and fragments. CollectiveUI does not put connection credentials into bot prompts, run snapshots, audit details or agent tool definitions.

Response redaction is display hygiene, not containment: it cannot prevent an adversarial runtime from encoding a secret or splitting it across separate message events. Credential/process/network isolation is the protection for the dashboard token. Provider and Runs credentials inside a user's runtime have the trust scope described above.

A bot-row lock prevents concurrent definition edits; a subsequent connection-row lock atomically reserves a lifetime key slot and a unique user×bot identity, then commits before remote I/O. Only one profile setup per user can run at once. A durable fenced lease coordinates workers. A create-intent flag is stored before POST; reconciliation only accepts the exact reserved name with its unique ownership marker. A preexisting name without that intent/marker is never overwritten. Partial failures keep the reservation, retry the same idempotent configuration, and expose no upstream error text. A managed run is admitted only after readiness, and snapshots the profile mapping ID. Resume, discovery and cancellation cannot provision a replacement. Model credential validity still depends on the operator; readiness does not make a paid inference probe.

For a rejected new message, the API checks storage before returning the exact `unsavedMessageId` the composer may restore. Saved prompts referenced by regeneration and duplicate requests are never marked unsaved. Approval retry has its own exact `retryApprovalMessageId`; a queue failure after persistence cannot remove the stored prompt. Cold cancellation and supersession use the immutable run context, retain an unconfirmed stop for reconciliation, and never route through an unscoped managed target.

Readiness still verifies seven surfaces on each admitted turn. The exact health/version gate runs first; the six independent authenticated reads overlap, with fresh user/bot/app/connection authorization before **each** dispatch. Joined binding reads remove redundant queries; no cross-request authorization cache is used. Database registration failures are classified separately from uniqueness conflicts, without exposing SQL or secret values. `/new` uses the existing transactional home-successor behavior; duplicate requests return the same fresh home and cannot duplicate profile creation.

## Verification

All feature validation uses synthetic credentials and either an in-memory transport or local mock HTTP listeners, plus disposable PostgreSQL. No real Hermes profile, external credential, container, deployment or production database was changed. Mock contract tests validate the adapter, not the behavior of a live Hermes deployment.

- `tests/unit/hermes-provisioning.test.ts`: exact blank-create/config/auth contract, lost response, ownership conflict, partial model setup, version/model/toolset/skill readiness, SSRF/default-profile refusal, body bounds and error redaction.
- `tests/integration/hermes-provisioning.test.ts`: admin/user access, shared-bot two-user separation, concurrency, retry/lease recovery, quotas, revocation, immutable admission binding, `/new`/resume routing, ownership, encryption and non-destructive retention.
- `tests/integration/hermes-provisioning-upgrade.test.ts`: upgrades the prior schema, preserves a manual connection/history/preferences and reruns migrations idempotently.
- `tests/e2e/hermes-provisioning.spec.ts`: actual admin/browser actions, owner selection, write-only secrets, ordinary-user administration denial, absent runtime, failed setup, restored drafts, regeneration failure with a saved prompt, distinct user routes, `/new`, frozen editor fields and mobile layout.

Run unit checks with `npm test -- --project unit`. DB tests require migrated `DATABASE_URL` ending in `/collective_profiles_test` and `HERMES_PROVISIONING_DB_TEST=1`; the upgrade test additionally requires a fresh `/collective_profiles_upgrade_test` in `HERMES_UPGRADE_DATABASE_URL`. Browser QA uses `playwright.hermes-provisioning.config.ts`, `HERMES_PROVISIONING_BROWSER=1`, local auth, that disposable database, the worker/web server and `tsx tests/fixtures/hermes/provisioning-server.ts` on loopback ports 19100–19103. The fixture creates only synthetic local accounts. Never point this test suite at a real installation.

Before production enablement, an operator must perform a separately authorized isolated upstream conformance run against the pinned deployment and prove its isolation/network/secret prerequisites. No live conformance was authorized in this task.

For the completed local validation and integration record, see [verification evidence](../security/hermes-provisioning-verification.md).
