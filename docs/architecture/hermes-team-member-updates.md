# Private Team resource updates

The member update service connects immutable Team revisions to a user's existing server-bound private Team profile. It does not replace Hermes learning or copy an administrator's used profile. Native member learning remains active whenever the verified runtime can run; these changes install only reviewed Team skills, role instructions and selected documents.

## API and identity

`GET /api/bots/:id/team/updates` returns only the current person's private preview. The optional `targetRevision` query previews restoration of an earlier published revision in that private instance. The response includes installed, target and currently published revision numbers; provisioning state; grouped actions; private conflict content and preview hashes; saved kept/deleted override previews; and any original pending request. A new conflict must first be recorded by applying the update before its resolution can be submitted. Saved overrides are separate from unresolved conflicts and allow an explicit hash-checked reset to the Team version.

`POST /team/updates` accepts `{expectedInstalledRevision, targetRevision?, requestId}`. `POST /team/updates/resolve` additionally requires `{packageId, choice, expectedMemberHash, expectedTeamHash}` with the two exact reviewed group hashes. Choices are `keep-member` and `use-team`. `POST /team/updates/cancel` accepts the original pending request UUID and can cancel only an untouched native replacement. Partial replacements must be recovered with that original request. All bodies are strict, bounded JSON with same-origin checks; all responses use `no-store`.

The service derives the person and member profile from current account and bot audience permission. A private binding does not grant access after removal from the audience. Requests never accept a profile name, runtime identity, filesystem path, manifest, application plan or progress receipt from the browser. Fresh authorization runs before every receipt lookup, after inventory, before native dispatch, and before database acknowledgement. Row locks run in bot, account, definition, profile and operation order to match audience/security mutations and avoid an account/bot deadlock. A failed acknowledgement cannot turn a revoked profile back on.

The injectable transport boundary returns unknown data. Snapshot and receipt validation runs before persistence. Production transport must independently recheck the grant and bound runtime/profile before and after its Docker helper, and terminate scoped helper work when its grant is revoked. Authorization at the web layer cannot close a native dispatch race by itself.

## Three-way preservation and transactions

The current immutable installed Team revision is the previous baseline. The latest or explicitly selected immutable Team revision is the offered version. Full bounded native inventory provides the current member copies, including added files within a tracked skill package and independently learned packages. Hash comparison happens on whole package boundaries. Modified, learned and deleted copies are preserved. Removed Team resources are removed only when the member's copy is unchanged. A package boundary cannot move into or out of a preserved ancestor package.

The service persists an immutable operation plan before native application. A unique request UUID binds exact input, source revision, target revision, definition version and private profile. Concurrent duplicate requests share the same operation; requests with different details cannot reuse that UUID. Every future retry uses the saved plan and original input. Pending preview uses that saved plan instead of inspecting a profile with parked resources.

Native completion and database completion are separate. Resource states, overrides, conflicts, installed revision and the complete operation receipt commit in one database transaction. Native completion before a lost acknowledgement is recovered by the protected native journal. A completed request does not run inventory or overwrite later learning. A resource completion or safe cancellation leaves provisioning state `connection_needed`; no inference route or gateway is verified in this increment.

Private restoration uses the same preservation rules and does not change the shared published revision. Shared administrative rollback separately reviews a historical immutable manifest and publishes a new monotonically numbered revision; it must not decrement a shared pointer or delete history.

## Native helper contract

`native-resources.ts` exports private inventory, safe publish selection discovery, filesystem application, update fencing and untouched-operation cancellation. The production broker supplies a canonical server-derived Linux profile root under the durable Docker owner binding; browsers cannot choose it. The broker must stop the native runtime, require all sibling controllers idle, hold an exclusive maintenance lease and check its generation and grant. Profiles within one person's container share that person's native environment and are not independent security boundaries.

`journalRoot` is a separate protected broker volume mounted only into the fixed resource helper, never into the native/user container. It contains compact plans' hashes, exact write groups and receipts. A native agent must not be able to manufacture a completed journal. The helper never treats a web application receipt as authority to skip native writes. Strict bounded journal validation checks operation/filename identity, group order, progress and exact recovery paths. Corrupt or unfinished journals fence native admission. Abort creates a protected tombstone even before the first write so delayed cancelled work cannot subsequently apply.

Each package is fully staged, flushed, parked and promoted through held directory descriptors and safe relative paths. Staging and backups stay on the retained native volume so rename boundaries are durable. The runtime remains stopped across the gap between parking and promotion. A crash after promotion is recognized from the exact reviewed content hash; a crash after parking is completed using the retained old package and validated stage. Partial or tampered state stays fenced for recovery rather than starting another update. Files excluded as private/auth/config within a tracked package block replacement so they cannot be discarded accidentally. Scripts and assets are copied as bytes and never executed.

The broker helper must use a fixed reviewed code bundle, the pinned Hermes image, no provider credentials, network disabled, bounded processes/memory/CPU and only its owned native and journal volumes. Capture and inventory use read-only native storage; apply/abort alone may write the native volume. This repository's filesystem fixtures validate the engine on synthetic roots. Docker helper admission and revocation guarantees are tested separately by the broker implementation. Live model/auth usage remains a separate bounded verification step and is not part of these tests.

## Evidence

The PostgreSQL/PGlite plus actual filesystem integration fixture teaches synthetic skill bytes in an admin working root, captures and publishes exact immutable packages, installs in Alice's private root, preserves Alice's modified/new/deleted skills, resolves a conflict and applies a newly published historical rollback. It also tests independent users, stale previews, removed audience permission, stale definitions, double clicks, lost native acknowledgement, native-complete database transaction failure, parked-package crash recovery, safe untouched cancellation and corrupt native receipts. Filesystem fixtures exercise every write checkpoint, unsafe links and paths, package boundary changes, secret-like content, strict protected journals and forged application receipts. No fixture invokes a skill, model, OAuth flow or live account.
