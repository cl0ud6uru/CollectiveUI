# Native Hermes settings and MCP administration

This panel extends the [personal remote workspace](native-hermes.md). Open a conversation and select **Native settings & MCP**. Settings distinguish the current chat from profile defaults. Changing profile defaults requires explicit confirmation because other clients using the same remote profile can be affected. The panel supports reasoning effort and speed tiers; Hermes remains authoritative about which tiers the selected model accepts.

Speed inspection uses the pinned native `config.set` handler's fixed `key: fast, value: status` query. That branch returns before any write and preserves `auto`/`cold`, including lazy chat overrides; `config.get fast` at this version reports those tiers as `normal`. Only an allowlisted tier is projected. A missing status method makes speed inspection unavailable, without a command fallback or inferred default.

The MCP panel displays server name, transport, runtime state, enabled state, tool counts and credential key names. It can test an existing server, install an uninstalled preset from the native catalog, add a typed custom HTTPS server, update an existing credential key on a configured server, enable or disable a configured server, remove a configured server, and reload MCP. Custom creation accepts only a bounded server name, an HTTPS URL without embedded credentials/query/fragment, and an optional bearer token. It calls the pinned `mcp.servers.add` contract with `config: { url }` and the native `bearer_token` field; the portal does not accept a generic config object, headers, command or arguments. The user confirms the profile-wide write before it is sent. Hermes stores the optional token in that profile's protected environment file; only a keyed digest receipt is kept by the portal. Before dispatch, the portal matches Hermes' exact name-to-environment-key normalization against the full bounded inventory and rejects aliases or an already-declared key. Because the pinned inventory redacts HTTP header templates, bearer-token creation fails closed when another HTTP server exists. The native add acknowledgement and a subsequent `mcp.servers.list` readback must both report the same config-owned HTTP endpoint; when a token was supplied, the native summary must also report header authentication. No native URL, token or raw server summary is returned to the browser. Concurrent portal custom-server additions serialize on the saved dashboard endpoint and profile across portal workers, and the inventory is checked again while that lock is held before receipt or dispatch. The pinned native API has no compare-and-swap for external dashboard clients, so this lock cannot serialize changes made directly in Hermes or by another portal installation.

Enable/disable uses the pinned authenticated dashboard `PUT /api/mcp/servers/{name}/enabled` route, not a gateway RPC; it is limited to inventory rows whose native provenance is `config`, sends the persisted profile, validates Hermes's exact name/state echo, and then requires native MCP inventory readback to match. This changes profile configuration for new sessions and other clients using that profile. Removal is limited to a `config`-provenance inventory row, requires confirmation, and succeeds only after the pinned native removal acknowledgement and authoritative list readback both confirm absence. Reload requires confirmation, uses the server-owned runtime identity, and succeeds only on the pinned native `reloaded` status. It can affect live sessions across the gateway and invalidate their prompt caches. The panel does not expose raw configuration, commands, arguments, environment values, headers, native error text or OAuth token values. Connection test results provide tool names/counts and the native token-presence boolean. A failed OAuth probe asks for sign-in only when Hermes explicitly reports tokens absent; failures with present or unknown token state remain generic.

MCP OAuth is a separate, explicitly confirmed user flow for uniquely inventoried, config-owned HTTP servers with supported names and no header authentication. It uses the pinned native-dashboard `POST /api/mcp/servers/{name}/auth?profile=…`, `GET /api/mcp/oauth/flows/{flow_id}`, and `DELETE /api/mcp/oauth/flows/{flow_id}` routes. The user opens the provider authorization link and completes consent; the provider returns to Hermes's own `/api/mcp/oauth/callback/{name}` route. Before exposing the link, the portal requires HTTPS authorization and an exact HTTPS callback under the connected native dashboard base, with one state and one redirect URI. The browser must be able to reach that native callback. HTTP-only dashboards, loopback callbacks, alternative callback origins and missing/mismatched metadata remain unsupported here; continue their sign-in in Hermes. Native OAuth storage maps punctuation to underscores in per-profile token filenames. Preflight checks the full bounded native inventory against that exact ASCII mapping, rejects filename and case aliases, and fails closed on names whose Unicode normalization cannot be proven safe. No HTTPS portal callback is invented. The gateway RPC's `client_redirect_uri` accepts only plain HTTP loopback with an explicit port; its `session_id` denotes an OAuth flow, not a chat. That client-listener contract is distinct from the native dashboard's supported HTTPS callback route.

The portal reserves a durable keyed start receipt before dispatch, never automatically repeats start, and returns an encrypted, ten-minute flow handle bound to the signed-in owner, connection, chat, saved conversation identity, profile, native flow ID, native destination, target fingerprint and authorization-URL digest. Native flow IDs are never accepted as standalone browser input. Provider codes, state and tokens do not pass through a portal callback or enter portal receipts. Polling rechecks current ownership, policy, destination, target and native flow identity; success requires both native `approved` status and authoritative profile inventory reporting OAuth credentials present. Opening the link or receiving a callback is not itself reported as success. Changed native configuration or authorization metadata leaves the outcome uncertain. Native configuration has no compare-and-swap across the asynchronous consent window, so external-client edits can only be detected by preflight/readback, not serialized for the whole authorization.

Closing the panel, changing scope, native activity beginning or expiry stops polling and attempts cancellation against the original flow binding. Cancellation remains available for cleanup when the chat is busy or new admission is disabled: only the authenticated, unexpired owner/chat-bound handle can request that fixed native DELETE. Durable ownership, destination identity and current destination approval still apply; cancellation cannot steer or start a grant. Cleanup is best effort if the browser closes or the network/destination policy changes; the native worker is bounded, and the user must check Hermes after an uncertain result. Native cancellation does not revoke an already approved grant: an `approved` cancellation response is reported as uncertain with grant-management guidance. Saved authorization is managed in Hermes or at the provider. Tests prove real native REST/callback routing, wrong-state/replay rejection and cancellation semantics at the exact pin with only the provider worker replaced; they do not claim a live grant or real token exchange.

The provider-account form adds one manually supplied API-key account at a time, through the pinned authenticated `POST /api/credentials/pool?profile=…` contract with `{provider, api_key, label}`. Confirmation explains that Hermes can use the credential for future requests by other clients sharing the profile and that Hermes may re-enable previously suppressed provider credential sources during the write. The portal appends a short request-specific suffix to the label, reserves a durable HMAC receipt, and never resends a request after an uncertain result. Hermes' response count is only a pre-reseed count: success instead requires a profile-scoped `GET /api/credentials/pool` to find exactly one newly created ID with that request label, manual source and API-key type. Other account rows may reappear after Hermes clears suppression. Token previews are discarded. Readback occurs only after the confirmed add operation, never when the panel opens. The form does not delete pool entries or initiate provider OAuth.

Every request requires the signed-in owner of the saved connection/session. The profile and runtime session identity come from the server's owned binding, never from request fields. For dashboard HTTP writes and their readbacks, the portal rechecks current admission, connection identity and private-destination approval under the settings/connection/session locks, resolves and pins the currently authorized address, starts the request before committing that dispatch envelope, then waits for the response outside the transaction. Changes and probes require an idle locked conversation row, no durable queue reservation, and an available runtime view with no running, uncertain or queue-pending work. Visible queued work also disables the panel's action controls. Profile administration is a remote profile operation, not a new portal tenant boundary: users must understand whether their Hermes profile is shared with other clients.

Mutations use durable receipts before dispatch. A repeated receipt returns an already-submitted response rather than replaying a possibly completed operation. Enablement uses only the pinned fixed authenticated dashboard route; removal and reload use only pinned fixed native methods; there is no generic RPC proxy. Protected credentials are sent only to the native setter and stored by Hermes; the portal retains only a digest receipt. The input is cleared on submit and panel close. Native errors remain generic and are not logged with request payloads. A lost response must be checked by refreshing the panel rather than automatically resending.

Methods are fixed and request schemas are narrow. Optional methods reporting `-32601` make the corresponding inspection unavailable; there is no generic RPC proxy or slash-command fallback. The native socket still requires readiness and server-request/approval capability negotiation. The typed custom-server operation uses the exact pinned `mcp.servers.add` fields `{profile,name,config,bearer_token?}` and result `{ok,name,server}`; list readback is required before success. Contracts were checked against Hermes `79af3f6cea8067284a7ea5725078578b3f790adb` and the managed runtime pin `f97608f178d1ffeca59860195ab7da295f7c8e5f`. Both support read-only speed status and distinguish absent OAuth tokens from failed connections with tokens present. The managed pin does not support `ultrafast`; Hermes rejects unsupported tier changes. Older versions may not offer these methods. Verification uses synthetic fixtures and exact-pinned source/conformance harnesses, not a live Hermes server.

Validation: focused administration, route, socket, session, reservation and migration unit suites; `node tests/browser/remote-hermes-administration.mjs`; the workspace browser fixture; targeted ESLint; `next typegen` and TypeScript. Browser fixtures use the real components with synthetic responses and check settings, MCP inventory/probes, preset installation, protected-field clearing, pending-work controls and stale snapshot rejection. Extracted handlers from both exact native pins confirm the lossy getter behavior, read-only status queries and token-aware probe results with synthetic state and no live I/O.

Implemented in this bounded slice: settings inspection/change, MCP inventory/probe/preset install, protected credential update, typed custom HTTPS server creation, user-driven MCP OAuth through a supported native HTTPS dashboard callback, manual API-key provider-pool addition, config-owned server enable/disable, removal, and confirmed MCP reload. Remaining: provider OAuth/account linking, unsupported MCP callback transports, provider-pool entry removal, stdio/custom-command server creation, provider/model selection and managed/local administration parity. Each needs its own verified native contract, ownership and active-work gates, and explicit confirmation where it changes shared profile state. An actual authorization grant remains an action the signed-in user completes with the provider. No general custom-config or workspace command proxy is implied. The panel reuses the remote connection/session/receipt schema introduced by migrations 0030–0032; it adds no migration of its own. Deploy using the complete current migration journal.
