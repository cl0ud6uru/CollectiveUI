# Personal Remote Hermes hub ownership

This protocol coordinates multiple portal instances that share one Hermes profile. A PostgreSQL lease selects a portal instance for one saved connection. It does not fence a process paused after its last database check. Before ordinary profile RPCs, session RPCs or prompt answers can be sent, the portal also requires the exact pinned Hermes native-owner adapter to accept and persist a profile-scoped generation. Native handlers and server-request answers check that generation at their execution boundary. Unsupported upstream Hermes versions fail closed for cross-instance takeover.

Authenticated client/capability negotiation precedes lease election and does not create, renew or take over a lease. It still checks connection identity and policy under locks. A successor can discover native support before attempting an expired-lease takeover; an unexpired foreign lease or unsupported native adapter still rejects takeover. Preparing a recovery candidate changes only the portal lease after those checks, without claiming native ownership or resuming work.

## Ownership and recovery phases

The portal lease binds connection ID, instance ID, lease generation and portal socket epoch. Hermes allocates its own monotonic native generation in the profile `state.db`; the portal never substitutes its database generation for that native proof. The authenticated WebSocket transport is bound to the full tuple. Same-profile clients compete through a SQLite immediate transaction and one native profile lock. Every regular method and server-request answer is checked under that lock against both the live native owner row and the socket-bound claim.

A transport can retain independent bindings for multiple resolved profile homes. Dispatch and protected answers select the binding from the actual target session/profile; a current binding for another profile cannot authorize them. The portal retains verified native proofs per profile. The connection lease's native-generation columns record its last persisted native claim and cannot represent every profile; profile proof checks use the exact cached claim alongside the current portal lease/socket, and native execution rechecks the durable profile row.

Queued native work carries the binding captured by its originating request and checks it again when the worker actually starts. Work already running remains counted until it returns. A new full owner cannot claim while a profile worker remains active. This is process-local activity accounting inside the single pinned Hermes gateway; the portal does not assume that transport close stopped a worker.

Confirmed recovery uses two native phases. The review candidate connects and reads capability/current state without claiming native ownership or resuming the conversation. Only after the confirmed intent is durably written does the portal claim `phase=recovery`. That claim fences old sockets, new admissions, ordinary RPCs and prompt answers, while permitting only the exact retained recovery ID and session to check status or call the pinned cancel-and-drain contract. The drain receipt must correlate the exact stored/runtime IDs, reservations, profile, boot and authenticated native principal. Recovery then promotes to `phase=full` only after that drained receipt is authoritative and no profile workers remain. A changed socket or lost acknowledgement is reconciled by reading the retained generation/receipt; the operation is never automatically replayed.

While a confirmed intent is pending or uncertain, the portal fences ordinary refresh/resume dispatch, incoming session-event persistence, server-request answers and session creation for the profile. Cache views may be shown as uncertain but do not settle durable state. The final session reset is a compare-and-set against the original lease, socket, session revision, ownership generation and recovery receipt. It clears the old runtime binding and increments its durable generation only after the exact drain and full-ownership proofs.

## Pinned implementation boundary

The native adapter is an explicit opt-in extension for Hermes commit `f97608f178d1ffeca59860195ab7da295f7c8e5f` (v0.21.5 desktop contract 8), composed after the separately versioned cancel-and-drain adapter. The installer validates a clean exact-pin checkout and is read-only unless `--apply` is passed. It does not restart Hermes, grant credentials, or change policy. The adapter is not an upstream Hermes capability. Runtime installations without this protocol remain usable by their current single socket, but a portal takeover that needs a native fence is rejected.

PostgreSQL lease rows and receipts contain identities, generations and bounded synthetic/native status only; they do not store prompt, answer, credential, or protected server-request content. Lease expiry, socket closure, idle snapshots, interrupts and process restart alone never prove terminal work. If capability, exact generation, boot-bound receipt, or readback is missing or stale, keep the state uncertain and do not retry the native action.

## Verification scope

Unit and synthetic loopback tests exercise lease serialization, stale cache/event/answer rejection, active recovery gates, native exact-pin composition, worker-start fences and receipt handoff. The optional PostgreSQL dispatch-lock test requires only `REMOTE_HERMES_LOCK_TEST_URL` pointing to a disposable loopback database named `collective_remote_lifecycle_test`; it skips otherwise and never uses `DATABASE_URL`. These checks do not represent a live Hermes grant, installation, multi-host deployment, or proof beyond the exact pinned adapter and its test fixture.
