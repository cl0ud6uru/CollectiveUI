# Disabled native Team adapter candidates

This increment implements candidate request handlers and a trusted native bootstrap. It does not enable Team chat, register a verified model/tool route, deploy an inference gateway or establish live ChatGPT access. `VERIFIED_TEAM_MODEL_ROUTES` and `VERIFIED_TEAM_TOOL_ADAPTERS` remain empty. Team conversation status remains `modelAccessAvailable: false`; broker `forTeamRequest()` and `controller()` still reject all Team inference. Existing personal Hermes startup is unchanged.

## Concrete production callers

1. The authenticated `POST /api/bots/[id]/team/runtime-candidate` accepts only a persisted run ID and model preference. `prepareTeamCandidateRun()` derives actor, bot, mode, native binding and profile from that run, asks the durable issuer for a short grant, and sends it through protected broker IPC. Empty verified routes reject before any provider credential is loaded.
2. Protected `POST /team/prepare-candidate` constructs a dormant `LocalController` using `DockerDriver.candidateTransport()`. Nothing calls its `start()`. A future verified native run could consume the fixed `gateway-candidate` transport; normal Team admission remains closed.
3. The candidate driver writes application-owned Python code, source hashes and opaque run grants in a bounded first stdin frame. The bridge checks the retained Team marker, canonical native identity, per-profile lifetime lock, exact image/source revision, bootstrap digest, expiry and pinned construction hashes before importing the gateway. Grants never appear in argv, Docker environment, native config files or broker JSON. Publication never supplies executable bootstrap inputs.
4. Native model URLs terminate at `POST /api/hermes-team/native/[contextId]/model/[purpose]/chat/completions` or `/responses`. The handler instantiates `createTeamModelGateway`, fresh authority and durable reservation dependencies. Model names, connection, billing actor and model purpose come from the server grant and fixed URL; body fields cannot change them.
5. The sole native MCP connection terminates at `POST /api/hermes-team/native/[contextId]/mcp`. The handler instantiates `createTeamConnectorService`. Only exact accepted tool schemas and an injected verified adapter expose a tool. Stored company connection credentials remain inside the server MCP client. Its authorization callback rechecks current permissions before every initialize, call and HTTP continuation.
6. Owner-only `GET /api/conversations/[id]/team/approvals` supplies private pending action/input previews. Existing-session, same-origin `PUT /api/hermes-team/approvals/[id]` checks the same actor, session, profile, native binding, installed revision, route proof and action/resource scopes. A pending MCP HTTP call waits at most 30 seconds, rechecks scope during every interval, and resumes its exact held request after the owner chooses Allow once. The existing Team chat controls mount familiar approval cards only for an admitted ready model connection and active conversation. They remain inactive in this build. Denial, revocation, disconnect or timeout starts no detached connector work.

## Native construction contract and offline evidence

Pinned Hermes is `f97608f178d1ffeca59860195ab7da295f7c8e5f`. The public `ProviderProfile.create_client()` hook in `providers/base.py` does not carry actor/profile/purpose. `agent/agent_runtime_helpers.py` catches provider-hook errors and continues through ordinary fallback, so that extension cannot establish a fail-closed Team boundary.

The candidate instead installs once in a dedicated Team gateway process before gateway import. It wraps these exact pinned construction seams:

- `run_agent.AIAgent` forces the fixed server custom-provider route and an immutable purpose on each instance. Constructor errors propagate; alternate model switching cannot change the server model.
- `agent/background_review.py:build_cache_parity_fork` constructs learning agents with the learning token.
- `tools/delegate_tool.py:_build_child_agent` and both imported `_resolve_child_runtime` aliases construct delegated agents with the subagent token. The instance purpose survives worker-thread context changes.
- `agent/auxiliary_client.py:resolve_provider_client` constructs utility clients with the utility token.
- `tools/mcp_tool_config.py:_load_mcp_config` and in-memory native configuration expose only the fixed Team MCP connection. Toolsets are restricted to native memory, skills, delegation and that connection; terminal, browser, direct company connectors and other unadapted native tools are excluded. Native learning implementations are retained.

The source-hashed Python fixture consumes the actual production bridge bootstrap, constructs parent/review/delegate agents and the actual auxiliary resolver, and makes two identical streaming SDK requests for each purpose to synthetic production HTTP handlers. HTTPX emits a fresh trusted UUID for every SDK call; SDK retries are disabled. Native MCP initialization/list/call uses the actual pinned MCP transport against the synthetic bridge. A socket guard permits loopback only. This proves those construction/client contracts, not a complete native conversational run or real inference.

SSE responses are bounded and buffered before delivery; the pinned streaming SDK consumes them successfully. Incremental streaming latency and stop/settlement during a full active native conversational run have not been established. Responses-mode constructors have not received the same complete offline constructor/streaming fixture as chat-completions mode.

## Receipts, attribution and private data

Migration 0041 adds candidate contexts, request receipts and human approvals without changing SQL/snapshots 0000–0040. Fixtures compare all 82 prior SQL/snapshot hashes and every prior journal entry with reconciliation baseline `bb2cae9d44b2a85a0b37d20584669a8826028960`. Fresh and 0035/0036/0037 upgrades preserve personal bindings, audiences, transcripts, learning usage and replay history.

Only SHA-256 bearer hashes are persisted. Native bootstrap holds plaintext opaque grants in broker/process memory. Each context binds the current actor/session, run, bot/version, mode, native identity, installed revision and immutable route proof. Candidate evidence must also pin a server-derived transport fingerprint covering actual provider/model/endpoint, organization/project configuration and encrypted credential revision; both fresh issuance and every request/approval reject a changed fingerprint without decrypting it. It lasts at most 120 seconds; another maintainer cannot reuse it. One active context per profile and unresolved request receipts fence overlapping native work.

Model receipts reserve at most 8 requests, 512000 input bytes, 2048 output tokens per context, and 256 output tokens per request. Confirmed provider input/output token counters populate existing `usage_events` once with server-derived user, bot, run and model purpose. Unknown usage attribution is committed with the dispatch claim before provider I/O. Streaming chat requests force usage counters; missing counters and failed I/O leave the same ledger row unknown, pause the context with `needs_attention`, and block all later purposes/nonces. Cash cost remains null. Reservations are conservative input/output allowances, not verified cash billing ceilings. Historical confirmed usage survives audience revocation; delivery and replay still require current authority. An ambiguous request becomes `needs_attention`, blocks later model calls and is never automatically retried or switched to another provider. Tool contexts allow at most 32 calls and 16 approval receipts.

Responses and approval arguments are private bounded replay data. Neither is returned in maintainer rollout views. A cached completed request only replays after fresh authorization. Unwrapped clients without a UUID use a conservative run/purpose/payload hash: identical payloads replay within that run, which can collapse legitimate repetitions. The trusted native shim's per-call UUID avoids this limitation for the tested model SDK path. MCP continuation retains the exact scoped request identity and consumes a matching human approval once. A timed-out wait retains pending approval data; it does not execute after disconnect, schedule work or promise automatic native resume. A later explicit matching call must independently recheck its still-current run and grant.

Native work after an app run becomes terminal cannot borrow the old run's actor/token, including background learning. It pauses at this boundary; a separately attributed durable background run/startup integration is still needed before enabling post-turn native background work. Runtime-wide Stop remains the existing container behavior; sibling-profile concurrency is not enabled.

## Remaining implementation and verification gates

- Personal access metadata reads only the current actor's existing encrypted ChatGPT connection row status/expiry. It never decrypts, refreshes, starts OAuth or reads native root/profile auth files. The existing connection represents native Codex, not the newer official OpenAI ChatGPT plan-usage integration.
- Pinned `plugins/model-providers/openai-codex/__init__.py` / existing `src/lib/llm/chatgpt/fetch.ts` rewriting strips `max_output_tokens`. Active personal Codex requests therefore reject before admission, reservations, credential decryption or provider calls. Required-personal mode makes zero company-provider calls for all four purposes. A bounded supported personal protocol must be implemented or independently proven before registration.
- Official ChatGPT plan usage has no tested native request/auth contract or implemented connector here. Its routes fail closed. Login success cannot change this.
- Native member MCP connection storage/ownership is not supplied by the pinned/app contract. `member_connection` has no concrete adapter and fails closed; it never selects a company connection. A supported member connector must be implemented before that policy can run.
- Alternate native paths remain unsupported: `agent/codex_runtime.py` external Codex app-server, `agent/copilot_acp_client.py`/other external-process providers, isolated compute-host gateways, hosted provider tools, multimodal/vision content, native terminal/browser tools, and arbitrary profile plugins. Native `agent/auxiliary_client.py` task-specific caches/async/raw Responses callers and gateway session/model rebind paths need complete construction/fallback coverage before an enabled inventory can claim whole-runtime support. Current exact source hashes and fixed request/purpose checks reject drift; they are not evidence that every alternate path is covered.
- Human approval continuation is implemented for an in-flight candidate MCP call and covered through actual GET/PUT handlers, server-side continuation and a mobile browser fixture. Full native gateway tool-event/retirement behavior during approval, reload, timeout and Stop still requires a complete synthetic active-run lifecycle fixture before enablement.
- The broker's prepared native controller remains dormant. Admission/worker routing that starts it, durable post-turn learning runs, usage-limit enforcement against a real provider, complete streaming native-run settlement and any verified route inventory remain deliberately unfinished until those compatibility proofs are available. This is not a usable pilot or proof of model-policy integration throughout a real native run.

The next safe step is a disposable pinned-image, synthetic HTTP active-run fixture covering gateway session creation, teach/learn, scoped MCP approval, streaming Stop and sibling interruption. It requires no live account, model credential, OAuth grant, company provider or deployment. Any later live provider/auth proof needs explicit authorization naming the integration/model, synthetic accounts, token/cash bounds and expiry/revocation cases. Current build authorization forbids live OAuth grants, live credentials and paid inference; no such test ran here.
