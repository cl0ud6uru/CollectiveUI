# Personal Docker Hermes

Personal Hermes is opt-in: first **Enable Hermes** creates one isolated Docker runtime for an enrolled CollectiveUI user, then pairs its native `default` profile to a private bot named **Hermes**. Additional bots use native profiles in that same runtime. New bots use the built-in Moss companion, with no catalog artwork prerequisite. This does not change the organization's default coordinator. Names and avatars remain editable.

Settings adds one collapsed Personal Hermes section under Connected accounts. The normal bot editor's existing Hermes connection selector offers **My Hermes runtime · new private profile**. Existing Skills and Memory panels display escaped, read-only native content and Refresh; there is no native installation/editor UI. Native chat can change its own resources under normal Hermes approval rules. Externally created native profiles appear only in **Unlinked profiles → Add as bot**. Backups, arbitrary marker-only directories, symlinks, default and already-bound identities are excluded. Renamed/replaced profiles require operator reconciliation; a binding is never silently reassigned.

## Migrations

Saved provider connections (`0023_saved_provider_connections`) are followed by `0024_docker_hermes_enrollment`, which adds default-denied enrollment permissions and durable cleanup status. Run the complete migration journal, not individual SQL files. Neither migration creates an enrollment.

The native RPC/controller foundation was developed in PR30, but its host-process installer, host setup UI, and compose overlay are not enabled here. PR30 and PR35 remain parked; neither must be merged/deployed first. Remote/manual and advanced managed Hermes remain available. Private `ai_apps.provider_config.docker` and `bots` rows continue to hold immutable broker mappings, with a transaction/advisory lock and existing pet relations.

Pinned upstream source: official Hermes **v2026.9.24**, commit `f97608f178d1ffeca59860195ab7da295f7c8e5f`. The bridge verifies this source marker and the native handshake checks ping, approval requests, and exclusive submit capabilities. The selected official Linux amd64 image is:

```
nousresearch/hermes-agent@sha256:2fd023efbb8d3d2b0ce1a73d028b07370cff34f567cfe0e999553e8c327ea283
```

The corresponding arm64 release manifest is `sha256:93b4e2877a2f48f4474b6dd2b99386ae32c4c552d32639df1a869b3f13c50b5a`; arm64 is not lifecycle-tested here. Moving tags, arbitrary registry names and browser-selected images are rejected. Do not update the pin without rerunning the native protocol/lifecycle suite.

Official references: [Docker](https://hermes-agent.nousresearch.com/docs/user-guide/docker), [profiles](https://hermes-agent.nousresearch.com/docs/user-guide/profiles), [pinned source](https://github.com/NousResearch/hermes-agent/tree/f97608f178d1ffeca59860195ab7da295f7c8e5f). This release uses s6 initialization and native profile reconciliation; readiness waits for its supervised main service, seeded profile, and actual protocol handshake.

## Trust and isolation

This is hardened **trusted-user isolation**, not a claim that Docker is a perfect sandbox. A trusted host broker alone can invoke Docker. Neither web/worker nor native agent containers receive a Docker socket, host runtime credentials, other users' storage, privileged mode, published ports, or host PID/network namespaces. The broker's protected Unix socket is powerful: membership in its trusted group is equivalent to control of enrolled personal runtimes. Never expose it over TCP or mount it in an agent container.

The server derives owner IDs from fresh principals. Enrollment requires a database permission granted under Admin → Hermes; admins have no automatic enrollment or access to other users' personal profiles. Bot creation permission is checked independently using the existing tools/bot-creation policy. Both app actions and broker leases distinguish creation from existing chat access. Private owner checks apply to bot/app lookup, profile discovery/link/read, native commands, runs, streaming batches and cleanup. Shared snapshots, templates, duplication, group chat, delegation, service execution and routines cannot use personal bindings. Company connection and bot lists omit others' personal metadata.

Each runtime has a deterministic hashed owner name and exactly one native Docker volume at `/opt/data`. SQLite/WAL data stays on a native volume, not a Docker Desktop host bind mount. The only other mount is the trusted read-only Python bridge. Inspection checks image, ownership labels, mount destinations, capability set, resource limits, restart policy and actual network attachments. Storage collisions are refused. Defaults are 2 GiB RAM (no extra swap), 2 CPUs, 256 PIDs, 25 enrolled runtimes and 16 profiles per runtime. Official s6 bootstrap runs with only CHOWN, DAC_OVERRIDE, SETUID and SETGID; all native operations run as UID/GID 10000 with no-new-privileges.

Credentials/configuration remain native. Root-profile OAuth inheritance stays inside the same user's runtime. Resource views read only bounded regular SKILL.md and fixed memory files, without following symlinks, hardlinks or special files; known secret patterns are redacted. They never return config, `.env`, auth stores or raw native stderr. Redaction is defense in depth, not a general secret detector. Users control their own native code/resources within their container; hostile users require stronger isolation.

**One native writer per profile:** broker controllers hold a profile inode lock and reject detected independent native CLI/gateway processes. A cold enable stops/drains the previous container before reopening profiles. A preflight scan cannot prevent a trusted operator or approved terminal command from launching a second writer later: upstream native CLI does not honor the bridge lock. Stop UI ownership before independent CLI/gateway maintenance; do not launch another writer from an active bot's terminal. Profile create/list operations are supported; independent chat/gateway processes on an owned profile are not. This is an explicit trusted-operator restriction, not enforcement against arbitrary same-user code.

## Operator setup (review first; no installer runs automatically)

1. Use a dedicated Linux host/broker account with narrowly controlled Docker access. Keep web/worker in an account without Docker access. Install this repository's locked Node dependencies for the broker. Keep its source/config/state inaccessible to native containers and nontrusted users.
2. Prepare canonical private state and trusted-group IPC directories. Bridge source must be non-group/world-writable and world-readable (public code mounted for UID 10000). Config is operator-owned and never accepted from the browser.
3. Supply an absolute broker JSON file, for example:

```json
{
  "socketPath": "/run/collective-hermes/broker.sock",
  "stateDir": "/var/lib/collective-hermes-broker",
  "bridgePath": "/opt/collectiveui/src/docker-hermes/bridge.py",
  "namespace": "cui-personal",
  "image": "nousresearch/hermes-agent@sha256:2fd023efbb8d3d2b0ce1a73d028b07370cff34f567cfe0e999553e8c327ea283",
  "network": "internet",
  "memoryMb": 2048,
  "cpus": 2,
  "maxUsers": 25,
  "maxProfiles": 16
}
```

4. Start `npm run hermes:docker -- /absolute/broker.json` under an operator-managed supervisor. The broker does not load the app `.env`. Configure BOTH web and worker with `DOCKER_HERMES_SOCKET`. Enrollment is stored in the shared application database, never the environment. The worker must be running; it renews authorization leases every 15 seconds and completes durable app pairing.
5. An administrator grants **Allow personal Hermes** to specific users under **Admin → Hermes**. New installations start with everyone disabled. The page separately reports broker **Not configured**, **Unavailable**, or **Ready**; ready means the web app can reach the protected broker, not that every user runtime, worker, image pull, provider or egress configuration has been verified. Permission changes are audited with actor, target and time and never provision automatically.
6. The enrolled user chooses Settings → Connected accounts → Personal Hermes → Enable, then **Set up provider and model** for the paired bot. Return through that bot's **Hermes settings** link or Personal Hermes at any time. Progress distinguishes runtime readiness, a saved provider key, and an explicit connection test. No credentials are copied from the host/app or another user.

### Explicit migration from the legacy allowlist

Do this during an operator-planned application upgrade: keep the previous web/worker release stopped while applying the schema and importing its reviewed enrollment, then start the new web and worker together. Back up the database and retained broker journals/volumes first. The new release ignores `DOCKER_HERMES_ALLOWED_USER_IDS` during normal authorization; skipping the import leaves existing users denied, with retained data untouched. Do not run mixed old/new app workers because old workers still trust the environment.

1. Run `npm run db:migrate` against the intended application database. This creates no enrollment records.
2. In an operator shell, set an explicit `DATABASE_URL` and load the previous, reviewed `DOCKER_HERMES_ALLOWED_USER_IDS`. Supply an existing enabled application's admin user ID as the audit actor:
   ```sh
   npm run hermes:import-enrollment -- --preview ADMIN_USER_ID
   npm run hermes:import-enrollment -- --apply ADMIN_USER_ID
   ```
   These commands run from the release checkout with its locked dependencies or from that release's **worker** image, which includes the importer. For Docker Compose, pass the reviewed allowlist from the operator shell into a one-off worker container (after applying the migration, while normal web/worker services remain stopped):
   ```sh
   docker compose run --rm --no-deps -e DOCKER_HERMES_ALLOWED_USER_IDS worker npm run hermes:import-enrollment -- --preview ADMIN_USER_ID
   docker compose run --rm --no-deps -e DOCKER_HERMES_ALLOWED_USER_IDS worker npm run hermes:import-enrollment -- --apply ADMIN_USER_ID
   ```
   The worker service supplies the intended `DATABASE_URL`; the import command replaces its normal startup command, so no worker, broker or runtime is started. Use the new release's worker image for both commands. The standalone web image does not include this operator script.
3. Preview reports eligible count and SHA-256 prefixes for invalid, unknown, disabled, or already-recorded IDs; it never logs raw invalid input or credentials. Invalid/unknown/disabled IDs abort the entire apply transaction. Correct the input and preview again. Existing database records are always unchanged, including revoked users, so repeating this command cannot override an Admin UI revocation. No IDs means no enrollment; there is no grant-all mode.
4. Verify the Admin → Hermes permissions and audit log before resuming user traffic, then remove the obsolete allowlist from both environments. Keep the broker socket configuration. If the old web and worker lists differed, reconcile the intended authorized users explicitly before importing; do not silently combine lists.

Grant/revoke takes effect without environment edits or restarts after this migration. The worker renews leases from fresh database permissions every 15 seconds. Web reads, setup/profile operations and streaming authorization also check fresh permissions, including disabled users/session versions, and database errors fail closed. Setup dispatch, worker lease renewal, final bot publication and enrollment changes use the same per-owner transaction lock, preventing stale queued setup from renewing after a committed denial.

### Revoking and re-enrolling

Turning permission off commits denial and an audit entry before cleanup. The broker's explicit revoke endpoint invalidates its lease and returns a prompt stop receipt; native cleanup runs asynchronously so another user's lease cannot be blocked by a slow Docker stop. The Admin page records **Stop pending**, **Stop failed — retry required**, or **Stopped — data retained** and offers a retry button; refresh also reloads status. The worker polls pending/failed stops even when broker configuration is missing, in rotating batches of at most two. Healthy owner checks run concurrently; worker control RPCs have a three-second timeout and no database connection waits for native stop completion. The worker waits at most two seconds for each owner's lock; an owner busy with a slow setup/profile action is skipped (no lease, no revoke) and retried on the next tick, so it cannot delay other owners' renewals. An unreachable broker cannot be confirmed stopped: application access is denied immediately, and the broker's existing lease expires within 60 seconds if it remains alive. Re-enrollment is blocked until stop is confirmed, then the user can explicitly Enable again; retained owner/profile IDs and volumes are reused. There is no data purge or credentials control on this page.

### Native profile settings

The persistent `/bots/<id>/settings` page edits the selected native profile, not a CollectiveUI model connection. The editor supports API keys for OpenAI (`openai-api`), Anthropic (`anthropic`) and OpenRouter (`openrouter`), native ChatGPT / Codex subscription device login (`openai-codex`), an exact model ID, and two collapsed advanced defaults: reasoning effort and maximum agent turns. The UI accepts 1–1000 turns or blank for native unlimited. It preserves unrelated native configuration; native per-model/session overrides may still take precedence. Start a new chat after changing defaults. Skills and memory remain read-only in their existing panels.

The compatibility contract is the pinned source's [`hermes_cli/config.py`](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/hermes_cli/config.py), [`credential_lifecycle.py`](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/hermes_cli/credential_lifecycle.py) and [`auth.py`](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/hermes_cli/auth.py). The bridge uses native configuration and credential helpers and verifies their resulting stores. Credentials travel over the owner-checked application route and protected broker socket, then Docker exec stdin; they are never returned in settings responses, stored in the app database, placed in command arguments or written to logs. The form offers explicit keep, replace and clear actions. Clear removes the selected provider's profile key and disables that provider in this profile, preventing inherited root credentials from silently taking over. Adding a new key reenables it. Other providers/sign-ins are preserved.

Other OAuth providers, custom endpoints, alternate native credentials and mixed native authentication pools require operator/native maintenance. Unsupported routes or advanced values are detected before stopping the runtime or saving. There is no arbitrary config/file/shell editor, model-list fetch, infrastructure privilege switch, or non-native OAuth implementation. Container resources, egress policy and runtime controls belong to the user's shared runtime, not an individual profile.

The actual image starter (`provider: auto` with the stock OpenRouter URL), no-op `openai_runtime: auto`, and saved stock provider routes are editable. An explicit provider change removes only the previous stock `model.base_url` and `model.api_mode`; a same-provider edit retains them. The guard checks full endpoint identity and both source and destination authentication, including pool endpoints. Legacy endpoint aliases, custom overrides and credential pointers remain protected. Missing provider capability means the app/broker/bridge versions need checking, not that native credentials need rewriting. Provider changes clear the draft model ID; switching back restores the saved model and discards unsaved keys.

Changed saves require **all profiles in that user's runtime to be idle**, including pending approvals. A broker admission fence prevents already-dispatched requests from beginning work during maintenance. It stops and reopens the retained container to release native writers and cached credentials; the next chat opens its native gateway with the saved defaults. An unchanged save does not restart. Revision checks reject stale tabs. Native writes are staged with profile-scoped authentication, then published under a fsynced rollback journal; interrupted stage/write files are recovered before another native gateway is admitted. A failed or uncertain operation stops the runtime and requires explicit restart/reload. Volumes, sessions and resources are retained.

Connection testing is a separate consented action: one short provider SDK inference request, no tools/history, retries disabled, redirects disabled, a 15-second timeout and a small output limit. It may incur provider charges. Saving never tests automatically. A persisted request receipt prevents a retried test request ID from issuing another request; uncertain outcomes stay uncertain. Leaving the page discards unsaved keys; already-submitted operations may finish and are reconciled by reload. `network: none` reports a policy block without sending a request. Under proxy mode, ambiguous connection/403 errors explain that egress policy or provider access may be responsible rather than claiming the key is invalid.


### ChatGPT / Codex subscription login

Choose **ChatGPT / Codex subscription**, save a model ID, then explicitly choose **Sign in with OpenAI**. Enter the displayed short-lived code at the fixed OpenAI device verification page and approve with your own account. This is native Hermes provider authentication, separate from signing into CollectiveUI. The account must support Codex and may require OpenAI device-code authorization. Offline model suggestions come from the pinned `hermes_cli/codex_models.py` catalog; they are not a promise of account availability. The page separately reports stored sign-in and untested model access. This slice does not send a Codex inference probe.

The compatibility contract is the pinned [`web_routers/oauth.py`](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/hermes_cli/web_routers/oauth.py), [`auth_codex.py`](https://github.com/NousResearch/hermes-agent/blob/f97608f178d1ffeca59860195ab7da295f7c8e5f/hermes_cli/auth_codex.py) and native credential-pool helpers. The adapter reuses native device-code acquisition, token exchange and grant persistence. It uses the native bounded HTTP client for one poll at the fixed native endpoint, because the upstream complete poll helper blocks for fifteen minutes. It does not scrape a CLI, expose Hermes's dashboard, implement token refresh, accept browser-supplied tokens/endpoints, or change network policy. A process-wide 20-second operation deadline escapes native transport retry handlers. Both access and refresh tokens are required before committing a grant; native helpers reconcile the device-code credential pool and its suppression state.

Each selected profile receives a fresh grant. Tokens stay in its native `auth.json`; no app database or broker journal contains tokens or device codes. A login in the default profile can be inherited by other native profiles under Hermes's existing root fallback rules. Named profiles use their own login; rotating tokens are never cloned. **Disconnect this profile** removes the local native grant and disables Codex in that profile, blocking root fallback. This does not revoke the remote OpenAI grant. Mixed manually imported credentials and `codex_app_server` or custom endpoint routing require native maintenance.

Start/reconnect requires all of the owner's profiles to be idle, then restarts the retained runtime once to release native writers. Reconnect clears the previous selected-profile grant before requesting a new code: cancellation or failure leaves that profile disconnected. Pending login fences all new chat, profile creation/linking and settings writes for that owner. Polling does not restart the runtime and is rate-limited by the native session's interval (at least three seconds). The code/session is stored with mode 0600 only in that profile. Browser reload resumes it until expiry; leaving the page pauses polling. Cancel waits for any in-flight exchange and then removes its grant. Stale sessions cannot cancel a newer login; repeated request IDs do not create new grants.

Broker receipts bind request/session/profile and terminal state, with a bounded capacity of 128 attempts per owner (operator archival is required at capacity). Expiry clears pending state even if the browser is gone. Runtime stop/revocation/restart discards unfinished login. Native orphaned exchanges are cleaned before gateway admission; a session-matched native grant completed just before broker interruption is also removed on recovery. An uncertain operation fails closed, stops the runtime and requires explicit restart/reload. No token exchange is replayed after interruption. Owner, current enrollment, CSRF, native directory identity, revision and shared maintenance checks apply to every mutation.

With network `none`, start reports the policy block without requesting a code or changing native authentication. Proxy mode still needs reviewed `auth.openai.com` egress for login/refresh and `chatgpt.com` for Codex inference. Pending 403/404 responses follow the native protocol; these can also reflect a proxy block, so the UI does not claim an invalid credential. No egress allowance is installed by this feature.


### Network choices

Fresh deployments default to `network: "internet"` (also write it explicitly in new broker configurations). The broker creates a dedicated bridge named `<namespace>-<sha256(app-user-id)>-internet`, with owner/namespace labels, IPv4 NAT, IPv6 disabled and inter-container communication disabled. It refuses extra peers, attachments, published ports and configuration drift. This follows ordinary Docker outbound networking rather than Hermes' host-network compose topology. **Standard Internet is not a private-destination filter:** outbound traffic can reach LAN/private addresses, Docker-host services and metadata endpoints where the host routes them. Do not describe it as Internet-only isolation. Use the restricted proxy below when those destinations must be denied ([Docker bridge networking](https://docs.docker.com/engine/network/drivers/bridge/), [Hermes Docker guide](https://hermes-agent.nousresearch.com/docs/user-guide/docker)).

`network: "none"` remains offline. Native profiles, settings and local data work; provider sign-in and inference are blocked. Existing deployments retain their pinned `none` or `proxy` default. When an existing config omits `network`, the loader inherits `stateDir/deployment.json` (legacy missing pins resolve to `none`), not the fresh-install default. Existing owner journals without a policy inherit that same deployment pin. Never edit the deployment pin or change a legacy config to Internet to force adoption; use the explicit per-owner transition.

In **Admin → Managed Hermes → Personal runtimes**, allow enrollment first, then use the person's **Internet access** toggle. Confirmation names the person, all-profile scope, restart behavior and policy boundary. Turning a restricted-proxy user off and back on preserves their proxy policy. Changing from Restricted proxy to Standard Internet requires the separate explicit action and confirmation. Enrollment revocation is independent and retains its existing fail-closed cleanup.

The server commits an audit intent under fresh Admin/session, target account and enrollment checks, then rechecks those permissions before dispatch under the same owner lock. The broker fsyncs the request receipt before accepting it; the lock is released while Docker work runs, so the worker can continue lease renewal. Exact repeat request IDs return the existing receipt; changed payloads and stale policy revisions are refused. Audit `accepted` means broker admission, not completed migration. Poll the requested policy, actual inspected network, running state and latest receipt to confirm completion.

A transition fences all profile controllers and rejects busy/approval-waiting work or pending subscription sign-in. It snapshots the full supported native profile roster and exact original container ID, stops writers, renames the original to a receipt-specific retained container, and creates the replacement using the **required existing named volume**. A missing or unowned volume is refused. Complete profile names/identities and existing bindings must still match. The durable commit precedes deletion of the original container; the volume is never deleted. A running runtime restarts, a stopped runtime stays stopped. Failed or cancelled transitions restore the old container/network and leave it stopped. This is network/container rollback, not a point-in-time restore of native file contents: native startup may have written to the shared volume.

Broker startup and stopped-broker supervisor cleanup reconcile pending migrations using exact receipt identities before opening IPC. They independently stop both owned identities even if a backup is missing or cleanup fails. Uncommitted changes roll back; committed changes keep their policy and retry retained-container cleanup. Unconfirmed recovery blocks admission and requires operator reconciliation. No uncertain native turn is replayed.

For `network: "proxy"`, the operator must provide one **internal Docker bridge per owner with isolated gateway mode**, named `<namespace>-<sha256(app-user-id)>-egress`, labeled `collective.owner=<hash>`, `collective.namespace=<namespace>`, and `collective.egress-policy=deny-private-allowlist`. The broker additionally requires `com.docker.network.bridge.gateway_mode_ipv4=isolated`, and `com.docker.network.bridge.gateway_mode_ipv6=isolated` whenever IPv6 is enabled; trusted host interfaces are refused. Docker's ordinary internal mode still exposes bridge-address host services, so it is insufficient ([Docker gateway modes](https://docs.docker.com/engine/network/port-publishing/#gateway-modes)). Its only other peer may be the reviewed proxy (`collective.egress-proxy=true`, alias `hermes-egress`, port 3128, no native data mounts). The runtime has exactly this network, no default bridge or published ports, and fixed HTTP(S)_PROXY settings. The proxy must allowlist required provider/public domains, validate DNS answers and redirects, and deny loopback, RFC1918, link-local/metadata, private IPv6 and host/service destinations. HTTP CONNECT must receive the same treatment. Labels describe operator attestation; the broker cannot validate the proxy's filtering implementation. With that isolated bridge configuration, direct external routing is unavailable; the operator must also verify host-service, private-address and proxy-bypass denial on the intended Docker host. This proxy mode is not end-to-end tested with external providers here.

### Stopped-broker operator transition and rollback

Keep the original broker configuration and back up the broker journal, app database and native volume together. These commands never publish ports, change host firewall rules or purge native data. Preview is read-only; apply/rollback require the broker to be cleanly stopped (no live/stale lock or socket). For a crashed broker, run the supervisor's original-config `--stop-retained` cleanup first. Do not delete its lock manually.

```sh
npm run hermes:docker -- /absolute/broker.json --network-plan APP_USER_ID internet
# Stop the broker normally, or let its supervisor complete --stop-retained cleanup.
npm run hermes:docker -- /absolute/broker.json --network-apply APP_USER_ID internet
# Revert the latest reviewed request's policy using the displayed receipt UUID:
npm run hermes:docker -- /absolute/broker.json --network-rollback APP_USER_ID REQUEST_UUID
```

Operator apply/rollback creates an `operator` receipt, uses the same retained-volume replacement/recovery path, and leaves the runtime stopped. Rollback refuses a stale receipt UUID. Review the returned policy, actual network and `committed` receipt before restarting the broker and letting the user explicitly start their runtime. An unresolved missing identity/volume/configuration mismatch is not permission to create replacement storage or adopt an unrelated container.

### Provider connectivity onboarding

Bot Hermes settings show four separate states: runtime, provider network, account authentication and model access. **Check provider connectivity** is an explicit, bounded DNS/TLS-only operation inside that owner's runtime. It uses fixed domains (`api.openai.com`, `api.anthropic.com`, `openrouter.ai`, or both `auth.openai.com`/`chatgpt.com` for Codex), with certificate verification and the actual fixed proxy route in Restricted proxy mode. It sends no provider HTTP request, key, OAuth grant or inference; Offline returns a policy block before probing. The bridge caps the total check at eight seconds and emits only sanitized outcome codes. Results are cached briefly for the saved settings revision and cleared by policy changes. Custom native routing must be reconciled first.

A reachable TLS handshake proves neither account sign-in nor model availability. API-key inference tests retain their separate explicit paid-test consent and receipt. Codex sign-in remains a separate secure device flow. Offline guidance directs the user to an administrator's per-person toggle, rather than requiring them to install egress infrastructure.

### Stop, revocation and crash recovery

The broker pins its deployment configuration in `stateDir/deployment.json`; changing namespace/image/deployment-default network or other configured values is refused until an operator plans a stopped-runtime migration using the original config. It never silently selects a new volume while stranding the old container. The broker stores fsynced owner journals and write-ahead bot/app IDs outside native containers. Repeated/parallel enable/create/link requests reuse mappings. Only successfully handshaken bindings are published. Application pairing is idempotent and can complete after reload/worker restart. A restarted broker stops retained runtimes before serving requests; it never silently resumes uncertain chat turns. Creation receipts retain profile names and reject changed request payloads.

The worker stops disabled/revoked/unregistered owners and invalid private bindings. Missing lease renewal stops active runtimes after approximately 60 seconds **while the broker is alive**. Failed stops remain an explicit error and are retried, never reported as stopped. Normal stop/cancel/setup failure preserves the container's volume, native sessions, skills and memory. A failed native transport stops the whole owner's container, so sibling profile chats can be interrupted; the UI should be explicitly restarted after that failure.

**A dead broker is not a watchdog.** `--restart no` does not stop already-running containers after a broker crash. Deploy with supervisor failure cleanup before enabling real accounts. For systemd, configure an `ExecStopPost` invoking the same locked Node/tsx entrypoint with `/absolute/broker.json --stop-retained`; use the same broker account and private config. That command refuses a live recorded broker PID, verifies each retained owned runtime, stops it, and clears the stale lock only after confirmed cleanup. Do not blindly delete `broker.lock`. An operator must reconcile Docker/configuration drift that prevents verified cleanup. Supervisor SIGKILL/host-reboot behavior still requires a staging check on the intended host; no live systemd or firewall change was made in this work.

There is no purge/uninstall-data endpoint. Removing enrollment stops access but retains data. Back up both native volumes and broker journals/app database together; losing mappings is not permission to adopt another directory or silently switch ownership.

## Disabled Team resource maintenance

The opt-in Team broker supports `/team/inventory` and `/team/capture` for current admin grants, and `/team/member-inventory`, `/team/apply`, and `/team/abort-update` for current member grants. The application derives the actor, audience, mode and policy before requesting a short-lived grant. Only the durable Team binding supplies the native profile name and inode; requests cannot supply native paths. Replies, native background learning and subagents remain unavailable until the full model route is verified.

Maintenance obtains idle holds on every known sibling controller, closes admission and stops the entire owner container. It refuses live conversations, pending approvals, uncertain cleanup and overlapping network changes. Read operations use a read-only mount of the retained native volume. Apply and safe untouched-abort operations receive that volume writable. These are fixed Node helpers from application-owned bundled code: networking is disabled, root filesystem is read-only, capabilities are dropped, resource limits are fixed, Docker logs are disabled, and skill scripts/assets are copied as data without executing them. The pinned image must already be present; helpers use `--pull never`.

Update journals live in a separately labeled per-owner volume mounted only by the helper. Native agents cannot edit receipts or recovery progress. A metadata-only initializer uses UID 0 with only `CAP_CHOWN`, without mounting native data; it masks the image’s declared `/opt/data` volume with a read-only 4 KiB tmpfs. All data operations use UID 10000 with no capabilities. Pending, partial or malformed journals fence capture, inventory and native reopening. Retries use the same immutable operation and plan; protected native receipts preserve later member learning after completed replay. A stale attempt may be aborted only before resource replacement has begun; aborted operations retain a protected tombstone. Partial replacements require recovery with the original plan. No native profile or history is deleted.

Browser-facing selectors are limited to 96 KiB; server-derived historical member-boundary metadata is limited to 2 MiB and 1024 IDs. The trusted update protocol allows 160 MiB of input and 64 MiB of output, accounting for bounded resource arrays, base64 and worst-case JSON escaping. Each resource snapshot retains the engine's 256-file, 1 MiB-per-file and 8 MiB-total limits. Owner cancellation invalidates helper admission and confirms helper/container cleanup before reopening. The interruption boundary is runtime-wide; same-person native profiles are not separate security sandboxes.

Read-only source fixtures, real filesystem recovery tests, bundled helper tests and a synthetic Docker daemon validate these contracts without model access. A bounded Docker smoke test against the cached pinned image remains necessary before a pilot: retained-volume mounts, UID ownership, helper lifecycle/cleanup, journal fencing across daemon restart and two sibling profiles must be exercised on the deployment host. This implementation does not pull that image, grant OAuth, enable a model route or enable the pilot.
