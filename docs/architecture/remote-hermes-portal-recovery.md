# Owner-confirmed native reservation recovery

An unknown prompt or queue acknowledgement keeps the portal reservation blocked. An idle snapshot, successful interrupt, disconnected socket or native close reply cannot prove the original operation stopped. The owner can review recovery, then explicitly confirm cancellation of unresolved work in that conversation. The portal never resends a prompt or protected answer as recovery. Completed output and native conversation history remain; prior external effects may still be uncertain.

This path requires both explicitly installed native adapters: `collective.cancel-drain.v1` (PR247) and issue96's native ownership fence with recovery/full phases. An older portal hub, missing capability, unsupported child/slash worker or unavailable native runtime fails closed. These are optional adapter contracts, not APIs supplied by the unmodified pinned dashboard. No adapter installation or deployment is performed by this change.

## Durable intent and two-phase ownership

Preparation connects the actual socket and probes capabilities without claiming native ownership, resuming a conversation or cancelling work. It captures the authenticated owner, connection, profile, portal/native/stored session IDs, exact session revision and ownership generation, portal lease owner/generation, actual socket epoch, exact prompt/queue reservation set and a SHA256 digest of the connection identity plus encrypted credential envelope. This immutable base binding contains no prompt text, protected answer, plaintext credential or raw native diagnostic. Credential rotation invalidates confirmation conservatively. An already-confirmed intent is returned before any refresh/resume.

The confirmation expires after one minute. Confirming atomically persists the same durable UUID as pending before native ownership changes. Confirmed intents fence ordinary event/snapshot reconciliation and session.resume dispatch. Lease and identity validation still apply. Workspace polling pauses while the dialog is open; server fences remain authoritative for other tabs and processes.

A recovery-only native claim CAS then fences obsolete transport dispatches and answers. Existing workers remain counted and uncertain; the claim does not assert they stopped. Only recovery capabilities/status/cancel-and-drain may cross this transport while the claim is in recovery phase. Native ownership is profile-scoped, so unrelated conversations on that profile may pause; they are not silently cancelled. The exact claim proof, including its independent native generation, phase, recovery UUID and runtime/stored-session IDs, is persisted separately from the immutable base binding before cancellation.

Native cancellation is dispatched at most once, after a durable native-request marker. Subsequent checks query the same native UUID. Idempotent ownership phase claims may be reconciled for that same UUID/connection/instance/lease/socket/runtime tuple after a lost claim reply; this does not replay a prompt, answer or native cancellation. If the portal crashes after recording the request marker but before native admission, the intent stays blocked. A missing journal row does not authorize reset or replay.

The strict native client validates protocol, runtime/stored IDs, UUID and exact reservation IDs. Validated receipts are retained even when later local settlement fails; a pending reader cannot overwrite stored drained proof. A `drained` receipt with reason `drained` is required before a separate native CAS can promote the same recovery transport to full ownership. That promotion requires the exact current-boot native drain journal entry and no tracked workers; its native generation must advance exactly once. A lost full-claim reply can reconcile only the same transition, without silently rebinding a different socket or lease.

Only the full native claim proof plus unchanged credentials, socket, owner, revision, ownership generation and reservation set permit the local transaction to clear reservations, set runtimeId to NULL and increment both revision and ownership generation. The full proof, terminal receipt and applied state commit atomically with release. Existing turn receipts remain. Cache invalidation follows commit and checks the new generation. A later resume creates a fresh native runtime; original work is never automatically submitted.

Pending, invalid, foreign, stale, missing or unavailable evidence leaves reservations blocked. A process restart or socket/owner takeover never silently rebases an old intent. The UI reports unverified recovery and offers an explicit evidence check. This protocol does not establish rollback of external effects, detached-resource teardown or general distributed exactly-once execution.

## Verification boundary

The focused PGlite suite executes real durable-intent and transactional-release code with synthetic ownership/transport responses. It tests revision/generation/runtime/profile/stored-ID/credential/socket changes, owner and confirmation boundaries, exact receipt matching, lost cancellation and full-claim replies, same-UUID checks, concurrent confirmation, expiry, pending proof, retained receipts and cache invalidation. The API suite checks origin/authentication before dispatch, bounded strict input and diagnostic redaction. These tests alone do not prove the native ownership adapter.

The opt-in `REMOTE_HERMES_PORTAL_RECOVERY_CONFORMANCE=1` integration suite starts the actual dashboard from a tracked exact-pin archive with both reviewed adapters applied only inside its disposable home. Production portal recovery/hub/socket code uses the named loopback `hermes_fixture` PostgreSQL database. Cases cover completed work with lost acknowledgement, an interrupt-ignoring active worker and protected-request ownership: recovery-only ownership must leave reservations blocked and ordinary admission denied until the worker actually ends, then exact drain/full-claim/local CAS can complete. History/turn receipts remain and the original request cannot replay. The active case starts real notification pollers for two conversations on the target profile and one on another profile: recovery stops and awaits only the target-profile pollers. A delayed worker and the published auxiliary starter must not enter under recovery-only ownership; after full ownership the auxiliary target must execute inside native active-worker accounting. Profile aliases must read the same recovery generation and cannot claim full ownership or mutate model configuration without terminal proof. An actual protected request whose session record is temporarily detached must reject an unowned response without settling its waiter. Unclaimed WebSocket and stdio dispatch/answers are rejected; the full owner alone resolves the exact open protected request, and missing/stale request IDs fail closed. Synthetic authentication and agent construction remain at the fixture seams; the synthetic agent implements the native assistant-persistence and unwrapped protected-answer contracts; Python socket/subprocess guards are fixture protections, not an OS sandbox. Actual adapter installation, live authentication, inference and deployment are not tested or performed.

For local composed native/transport debugging without a PostgreSQL server, `REMOTE_HERMES_PORTAL_LOCAL_CONFORMANCE=1` runs the same three cases through PGlite using the opt-in unit wrapper. This is explicitly not PostgreSQL lock/failover acceptance. It uses only the fixture migrations and a mocked database module; no PostgreSQL driver/pool is constructed. The real PostgreSQL integration job remains required.

```sh
REMOTE_HERMES_PORTAL_LOCAL_CONFORMANCE=1 \
HERMES_SOURCE=/path/to/clean/exact/pin \
HERMES_DASHBOARD_PYTHON=/path/to/isolated/python \
ENCRYPTION_KEY=synthetic-conformance-only \
npx vitest run --project unit tests/unit/remote-hermes-portal-native-conformance.test.ts
```
