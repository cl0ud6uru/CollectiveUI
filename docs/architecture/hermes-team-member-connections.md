# Personal MCP accounts for Team Bots

This increment supplies a server-side candidate account adapter. Production native tool verification remains empty and Team chat admission stays closed. It does not establish an OAuth grant, connect an account or enable native inference.

An admin fixes a capability to `member_connection`, one reviewed MCP server, one action and a resource scope. `connectionId` identifies that server template. Every native request resolves the current actor's unique `mcp_member_connections` row for the template. Missing, expired, disconnected or stale accounts require that person's connection; shared server headers and signing secrets are never used as a fallback.

Migration `0042_hermes_team_member_connections` creates owner/server-unique account rows with mandatory expiry. Credentials are encrypted personal HTTP headers. Additional authenticated encryption binds the ciphertext to the row, owner, server and reviewed target hash. The target hash covers the fixed URL/transport, reviewed server/tool policy and tool snapshot. This new table accepts only authenticated `v2` ciphertext; legacy ciphertext without those bindings is rejected during opening and key rotation. Editing that target invalidates the old account before credential decryption or initialization. An explicit owner save re-encrypts against the new target and advances the revision. A database trigger prevents reassignment and requires every mutation to advance the revision once. Local disconnect clears the stored credential while retaining account metadata and private history; it does not revoke the key at the outside provider.

Private `GET`, `PUT` and `DELETE /api/bots/{id}/team/connections/{capabilityId}` derive the person and endpoint on the server. GET returns only that person's status/revision/expiry. PUT takes `{expectedRevision, headers, expiresAt}`; DELETE takes `{expectedRevision}`. Mutations require a same-origin authenticated session and a freshly authorized member-required capability. The current member audience or an assigned admin maintainer may manage their own account; general admin status grants no access to another person's account. Header input is bounded, uses Fetch's wire-value normalization and rejects HTTP/session/portal identity overrides. Personal and shared result redaction masks normalized header values and bare Bearer/Basic credentials as well as stored values. HTTPS endpoints and an expiry within 30 days are required. Credentials never appear in response metadata, native profiles, tool listings or admin rollout status.

`GET /api/bots/{id}/team/connections` lists only fixed required accounts for the current actor. Its setup catalog is unavailable while production adapter verification is empty, so the ordinary UI can show status without collecting credentials or exposing header configuration. A stored `connected` state means a credential was saved, not that the outside account has been authenticated. `GET /api/hermes-team/member-connections` lists retained own metadata for Settings cleanup after audience or capability removal. It returns up to 100 entries and `nextCursor`; optional `cursor` pagination accepts an account UUID. `DELETE /api/hermes-team/member-connections/{id}` revokes that retained owned account with `{expectedRevision}` and a fresh enabled session. These cleanup routes grant no renewed Team capability or tool access.

The native service binds exact personal account/target hashes to tool attribution and approval. It checks the current person, audience, capability, action/resources, server controls and account before initialization, each transport request, tool dispatch, completion and held approval continuation. Server and bot approval requirements are both enforced. Rotation, expiry and disconnect invalidate queued work and stale cached replays. Confirmed private results redact personal header values before caching. Every unresolved reserved, running or attention receipt fences another connector dispatch in the same native context, including a fresh request UUID after a crash. An ambiguous action is not repeated automatically.

The synthetic fixtures use actual PGlite migrations and the pinned MCP SDK with an in-process mocked HTTP upstream. No real secrets or external connections are involved. The current candidate supports owner-provided static HTTP authentication only. Provider-specific account identity verification, OAuth consent/refresh/revocation, real MCP endpoint behavior and native full-chat lifecycle verification remain separate gates before any route can enter the production verification inventory. Background native learning receives no member or company MCP tool grant.
