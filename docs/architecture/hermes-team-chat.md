# Hermes Team Bot chat increment

The application and Docker broker flags remain off by default. The existing editor and chat now support Team configuration, separate member/Admin conversations, lazy native profile reservations, and retained provision/retry states. Admin mode requires current administrator status plus this bot's maintainer assignment. A maintainer outside its audience opens the working context directly; this never creates a member grant.

Members and maintainers have different native owner keys. Member profiles share that person's existing Docker container, while the working bot uses a dedicated admin owner. Profiles organize native agents inside one container; they do not isolate those agents from each other. The broker creates blank, parked profiles without seeding personal root resources. Native tool/settings routes and the existing company app cannot bypass the Team execution block.

Opening a chat renews authorization and validates the retained native identity. Configuration changes during setup reject binding, and bot-before-profile locking prevents conflicting settings from being persisted. Retries retain the reservation and never reassign a private profile. Models remain unverified and replies stay blocked; `connection_needed` is deliberate even when provisioning succeeds.

The UI keeps the pet and chat controls, identifies Admin mode, and explains shared working learning. Native iOS presents an explicit web-compatible state and blocks inference/approval/regeneration fallbacks for Team Bots. Publication and conflict actions depend on later increments. Native settings, groups, routines, templates, and legacy memory extraction do not operate on Team profiles.

Verification includes real component browser fixtures at mobile and desktop widths, synthetic migrated-database authorization/provisioning fixtures, origin/body boundary fixtures, and broker/bridge identity tests. Real model/auth and original-image lifecycle tests remain separate enablement gates.
