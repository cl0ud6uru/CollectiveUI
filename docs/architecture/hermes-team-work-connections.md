# Shared Team Bot, personal work connections

This dormant increment extends the existing Team Bot and official-plan candidates. Jason and his boss can use one shared Audit Bot definition while each member retains a private profile, runtime, conversation, learning, tools and credential connection. Select `personal_required` in the server Team model policy to require each initiating person's own selected registration. OpenAI binds that issued client to the person and workspace chosen during authorization. A user label such as Work describes their selection; it is not verified Business membership. The optional `personalWorkspaceId` capability adds a stricter allowlist only if separate trusted evidence becomes available; it is not required for per-registration isolation. A shared definition is not permission to use the maintainer's connection. The authenticated actor is retained in the run context for reply, learning, subagent, utility and replay; existing membership, session, policy, account and credential binding checks still run before dispatch, while reading the stream and before output delivery. Errors never select company/API spend or another person's account.

Migration0048 adds nullable provenance to official connections and durable protected-transfer receipts. Legacy connections retain their ciphertext and catalog unchanged; they cannot meet a workspace-bound policy without a verified transfer. Provenance binds the owner, issued registration client, verified subject, optional separately evidenced workspace, source host, destination host, adapter and exact transfer ticket. It has its own authority expiry and is authenticated as part of the credential envelope. Account-specific catalogs and token validity remain separate checks. Provenance is not a claim of Business entitlement or provider-host usage attribution.

## Supported transfer boundary

### Executable offline companion and receiver

The second increment implements the trusted source and receiver protocol rather than mocking `verifyHandoff`. Run `npm run test:official-companion` for the disposable demonstration: two authenticated synthetic app users complete actual local loopback requests, generated-provider JWT verification, protected storage, Ed25519 receipts, X25519/AES-GCM transfer and the server importer over local stdio. The shared Audit Bot test then exercises each caller's account for reply, learning, delegation, utility and replay. Generated keys exist only in fixture memory; all provider responses are mocked and temporary credential files are removed. No SSH server, account or access configuration is created.

`scripts/official-plan-local.mts` supports `sign-in`, `reconnect`, `status`, `refresh`, `transfer` and `recover`; `scripts/official-plan-receiver.mts` runs the receiver's bounded stdio dispatcher. Both entrypoints refuse operation by default. Their installed driver registries, the pairing inventory and the existing model/transfer release registries remain empty. `createApprovedLocalCompanionDriver` is the Linux implementation for an already approved private directory, pairing record and SSH destination; it invokes the local browser and uses the existing SSH credential/known-hosts configuration with `BatchMode=yes`, `StrictHostKeyChecking=yes` and no shell. No token, private key, PKCE verifier or ID-token hint is sent in a command argument or logged URL. Only the documented authorization request and inbound OAuth code use the browser callback; neither is printed or logged. Actual account tokens travel only in the encrypted protected-transfer payload. No local code or callback code is forwarded to the portal for exchange.

The trust boundary is explicit: a receiver installation obtains the current `Principal` from existing server authentication or an approved gateway identity adapter, rechecks the current database session, and independently resolves an operator-approved source-key/pairing binding to that app owner. Stdin cannot select the actor. The source installation pins the VM's signing and encryption keys and expected app owner; a self-signed sender key, arbitrary uploaded JSON, public host ID or digest supplies none of that approval. The receiver signs the exact owner/session/registration/destination ticket. The source validates it against its pairing, signs the full snapshot created by its locally validated token exchange, and durably suspends that journal before constructing an encrypted envelope. The receiver validates the approved signatures and exact credential/snapshot/custody/ticket digests, stages only private files, and repeats actor/pairing approval after provider I/O before installing the grant. This is authenticated application custody evidence, not provider attestation that every token copy in the world is absent. Compromise of an approved source's code or signing key compromises that source evidence and requires stopping/revoking its access.

Each source journal and receiver staging operation uses an exclusive lock and owner-only descriptor-bound files. Writes are atomic and fsynced. Source refresh has a durable intent and one rotating-token claimant; uncertainty never resumes the old grant. After suspension, only a freshly authenticated pending status can retransmit the same grant without refresh. A complete status recovers a lost acknowledgment without another import. Canceled/uncertain status transitions the source to `needs_attention` for fresh OAuth, never back to active. A completed acknowledgment removes source credential bytes while retaining registration metadata and history. Receiver cleanup removes only its staged credential file. Hard process crashes leave lock files fenced: an operator must confirm all competing source/receiver processes are stopped before recovering that specific lock and staging data. No PID guess, timeout, directory wipe or automatic stale-lock removal grants refresh ownership.

Both protected stores currently require Linux procfs; Windows/macOS credential-store support is not claimed. The actual browser must run on that supported local host. Installation drivers and receiver gateway authentication must be separately reviewed and registered after user approval; a source key bound only to an SSH user is not a substitute for independently authenticated CollectiveUI ownership. The receiver needs an approved private staging root outside every runtime mount, distinct persisted VM identity, approved actor-specific source public keys and private receiver signing/encryption keys. This code neither generates that production material nor configures access. Successful offline fixtures do not establish eligible deployment, real consent, model entitlement or allowance compatibility.

The [official self-hosted VM flow](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) completes OAuth on the browser's local machine with the same tool/client and selected user/workspace, then transfers the selected protected credential file over a secure channel. The destination preserves its own stable host ID and owns future refreshes. The portal cannot exchange a callback code forwarded from the laptop as a substitute for that transfer.

`startOfficialPlanTransfer` and `completeOfficialPlanTransfer` are internal trusted-adapter functions. They are not mounted as browser endpoints or CLI commands. Their default transport registry is empty. The start function takes the current server-authenticated principal and exact selected registration, captures the existing account revision, and creates a ten-minute ticket. A trusted adapter must separately verify a handoff receipt covering the exact normalized credential-file digest, ticket, owner, issued registration, source host and target host, and must prove the source relinquished refresh ownership. The source must authenticate the entire token set as originating in the same locally validated OAuth exchange, including its opaque refresh token. Independently supplied access/refresh tokens cannot be blessed by a valid ID token. If an optional corporate workspace allowlist is requested, its additional evidence cannot come from a user label or a workspace field in uploaded JSON. The receipt contract is application infrastructure, not an assertion that OpenAI supplies this receipt format.

The candidate reader uses this app-defined path:

```text
<operator-configured private root>/<sha256 CollectiveUI actor>/<transfer UUID>/credentials.json
```

The reader currently requires Linux procfs: it pins directory descriptors and opens each child beneath its retained parent to fence pathname replacement. The root and all directories must belong to the portal service UID with no group/other permissions; the file must be a regular, singly linked owner-only file. Symlinks, oversized files, changed files, invalid UTF-8/JSON and arbitrary browser paths are rejected. This staging root must be outside every user runtime/volume mount. Only the trusted transport can access it. The credential file contains `version:1`, `client_id`, verified `subject`, `source_host_id`, `access_token`, `refresh_token`, retained `id_token`, and optional `earliest_refresh_at`. This is a CollectiveUI adapter format, not Codex's native `auth.json`. All import I/O is bounded. Errors return fixed text, and secrets and filesystem paths are absent from status APIs. The reader neither erases staging files nor mutates a runtime home; the companion receiver cleans up only its own staged credential file after completion or failure. Hard-crash recovery remains explicit operator work.

The importer claims a durable receipt before reading and reserves a unique refresh-token fingerprint before verification I/O. Two imported copies cannot acquire independent refresh owners, even across users. Canceled, completed or uncertain tickets cannot resume after restart. A delayed completion rechecks the current session, selected account revision, ticket and provenance expiry before atomically installing the encrypted credentials/catalog. Reconnect leaves the old selection intact until verification succeeds, and never deletes volumes, conversation history or private learning. An uncertain replacement blocks model work for its prior account until reconciled or canceled. Cancellation fences the replacement; it does not itself revoke the old active account. Local/remote disconnect continue using the existing official revocation receipts, and an account revision change fences an in-flight replacement.

Refresh remains an explicit portal operation with one durable claim per credential revision. The source adapter must stop refreshing before import; the portal cannot prove that by checking a file permission. Refresh preserves the approved provenance and its expiry, and only the destination owns subsequent rotations. Unknown rotation results remain paused after restart. There is no automatic timer inferred from the opaque `earliest_refresh_at` field. Local disconnect clears the encrypted grant. Provider refresh-session revocation may affect other copies; it is not host-only revocation.

## Runtime and allowance compatibility

The current Team candidate uses its bounded server Responses gateway and pinned native purpose adapters, not a newly registered Codex app-server. Existing `/team/runtime-capabilities` readiness checks continue to prove the protected actor grant, runtime enablement and network access. These facts do not prove account eligibility, workspace membership or a successful model turn. No production model route or transfer transport is registered, and `connectAvailable` remains false.

The [SIWC Codex app-server configuration](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) supplies an access token as a custom Responses provider's `env_key`. It can return a bundled model catalog; it does not establish entitlement. Token renewal requires restarting app-server and resuming the retained thread. Its inference support does not establish that `account/read` reports `type:chatgpt` or that `account/rateLimits/read` and account-update notifications describe this SIWC session. Consequently this increment registers no allowance runtime and changes no allowance normalization. Unknown, sparse, stale and exhausted states remain distinct, with owner authorization at every cache/read boundary. Subscription token activity remains `chatgpt_plan` with null API cost; it is excluded from API dollar totals.

Native Hermes Codex device OAuth, the unofficial `chatgpt.com` backend provider, official SIWC plan usage and company API billing remain separate integrations.

## Remaining production blockers and approval handoff

The local OAuth, encrypted transfer, receipt verification and custody mechanism above is implemented and exercised offline. Remaining connection work is approved installation, pairing/identity-adapter configuration and live verification, not another generic OAuth rewrite. Database-backed receiver identity/pairing adapters must honor the provided transaction executor during final authority checks; otherwise they can deadlock the import they are authorizing. No approved production adapter is registered here.

The official [overview](https://developers.openai.com/siwc/token-sharing-open-source) covers open-source and locally hosted apps and directs paid/remotely hosted apps to a separate interest process. This saved cloud development environment does not establish that CollectiveUI's eventual deployment qualifies. The [registration guide](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) says an issued registration is bound to its authenticated person and chosen workspace. However, the [published token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference) exposes no workspace identifier; `sub` and email cannot verify that Jason's and his boss's separate registrations select the same Business workspace. Encrypted OpenAI auth metadata is opaque. This missing literal workspace claim does not block isolation by verified issuer, subject and issued registration. It leaves the separate corporate-workspace allowlist capability unavailable; no provider workspace-attestation API is invented. The remaining release blockers are approved installation and pairing of the implemented same-tool local authorization/secure-transfer adapter, live verification of its custody and identity adapters, deployment applicability and actual model access. Successful login and a model list cannot fill those gates. The current [Help Center guidance](https://help.openai.com/en/articles/20001542-using-your-chatgpt-plan-in-other-apps-and-sites) distinguishes supported open-source tools available to ChatGPT users from commercial plan sharing for Go/Plus/Pro. Neither generic Business eligibility nor generic Business exclusion is claimed for this deployment.

After a separate user approval for real authentication/persistent access, an operator must:

1. Confirm the eligible deployment and work-plan usage contract with OpenAI, including Business workspace controls. Do not enable flags based on login alone.
2. Install and pair the reviewed local tool/receiver on supported Linux hosts and register their approved installation drivers. Bind receiver gateway identity to current CollectiveUI authentication; approve separate source keys per app owner and pinned receiver keys/host identity. Use existing approved SSH access without silently changing credentials or known-hosts. Retain local PKCE/state/nonce validation, whole-set receipts and durable custody; keep staging outside runtime mounts. Do not substitute a pasted code, public callback or native Codex token file.
3. Verify the adapter's production provenance, token signature/claims, rotation/restart/revocation behavior and protected-file cleanup. Supply renewed custody evidence when provenance expires. Corporate-workspace allowlists need a separately documented source and must remain unavailable without it; an arbitrary adapter assertion is not proof of provider membership. A supported import currently requires a valid retained ID token for identity verification; an expired token is not accepted as fresh authority.
4. With approved synthetic live accounts, verify the selected model through a completed turn for every native purpose, helper, retry and utility route, and repeat revocation and membership-loss tests. Only then add exact server model route/transport evidence and consider default-off gates in a separately reviewed release.
5. Wire an owner-bound allowance runtime only after verifying its actual account/rate-limit contract. Otherwise show unavailable/unknown rather than an invented remaining quota.

The [OpenClaw Enterprise reference](https://github.com/openclaw/openclaw-enterprise/blob/fc7eb2f7a93adbaf1fa97f4b4995e848f5b4b6a1/docs/guides/integrations/chatgpt.md) was inspected at the requested commit. Its managed PAYG service accounts do not meet this per-person subscription requirement. Its separate native device-auth, private custody and runtime entrypoints informed the one-owner, cancellation and readiness checks. No code was copied, and its destructive Codex-home reconnect behavior was not adopted.
