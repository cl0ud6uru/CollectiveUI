# Hermes Team Bot publication API

The publication service reuses the existing Team Bot definition, audience and
maintainer records. Capture, publish and rollout operations require both fresh
administrator status and permission to maintain that specific bot. The disabled
`HERMES_TEAM_BOTS_ENABLED` gate applies to each operation and retry.

## Capture and review

`POST /api/bots/:id/team/capture` accepts `{ expectedRevision, selection }`.
Selection contains relative skill package names under `skills/`, `includeRole`
for `SOUL.md`, and explicit document names under `documents/`. A browser cannot
provide a filesystem path, native profile/runtime identifier, manifest or user.
The server-side transport derives the separate Admin mode working binding.

The service checks and records the current definition version and published
revision, releases its database locks, then requests capture through the broker.
The returned untrusted manifest is independently bounded and hash validated by
the resource engine. After I/O, a short transaction locks the bot/definition and
reauthorizes the person. A changed definition, published revision, account or
maintainer grant prevents saving the capture. No native I/O occurs while
publication database locks are held.

A saved capture contains exact safe resource bytes, actor, definition version,
base revision, manifest hash and a server-generated 15-minute expiry. The response
contains a `snapshotId`, hashes/version/expiry and frozen added/changed/removed
whole-package review units with actual previous/captured content. These are
administrator-reviewed team resources, never a member's private skills or memory.
Changes learned after capture belong to the next draft. Omitted prior resources
are removal candidates and require explicit selection to be removed.

The native broker has no verified volume capture helper in this increment. The
real capture operation therefore reports an explicit unsupported capability
response (503). Synthetic fixtures exercise persistence/publication without
model calls, grants, production credentials or native container changes.

## Publication and retries

`POST /api/bots/:id/team/publish` accepts `{ snapshotId, expectedRevision,
selectedKeys, removalKeys, releaseNote, requestId }`. Keys are whole package IDs,
including `skills/<name>`, `SOUL.md` and `documents/<name>`. `requestId` is a
persistent UUID generated by the UI for this one publication and retained across
retries. The note is a nonempty string of at most 500 characters.

Under the same bot/definition lock, publication freshly authorizes before looking
up any operation receipt. A completed exact request returns its original result,
including after the capture expires or later publications advance the bot.
Changing the payload under that UUID is rejected. Receipts are checked against
the corresponding immutable revision. Pending/inconsistent receipts require
attention rather than creating another release.

A new publication checks the current base revision, capturing actor, bot,
definition version and expiry. It merges selected exact capture bytes into the
previous immutable publication; unselected previous packages remain. A removal
must be in that frozen review, and unsafe or overlapping package-boundary changes
are rejected. No files are reread and no skill code executes. Empty/no-op releases
are rejected.

The pending operation, immutable revision, definition's published-revision
pointer and completed receipt commit in one database transaction. Concurrent
identical clicks produce one release; different stale reviews cannot both publish
against one base. A transaction failure rolls back all four mutations, allowing
the same UUID to retry. Migration `0039_hermes_team_revision_immutability` prevents
UPDATE and DELETE of published revision rows. Offboarding and rollback therefore
retain historical releases.

Both POST routes require authenticated same-origin JSON requests and bounded
bodies (96 KiB). Responses, including failures, are `Cache-Control: no-store`.
Errors contain no credential values or raw native contents.

## Rollout and remaining runtime work

`GET /api/bots/:id/team/publish` returns the current revision and aggregate member
profile states, profiles needing an update, and conflict counts. It does not
return member identities, profile IDs, private resource paths, contents or hashes.

`nativeUpdatesSupported: false` explicitly reports that no native filesystem
update adapter is shipped. Publishing does not claim installation and does not
change member profile states. The separate pure three-way planner preserves
member modifications/learning/deletions and supports rollback, but native
application, durable per-profile update receipts, conflict-resolution writes and
active runtime revocation require the verified volume helper and maintenance
lease before they can be enabled. Model route and native connector verification
remain separate gates; publication grants no model/tool capabilities.
